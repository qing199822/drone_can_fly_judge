## 1. 相机朝向控制（云台）

**证据**
```python
# ws2025/src/gimbal/gimbal_control.py
15: rate = rospy.Rate(30)
16: gimbal_pitch_ = -30                     # ← 固定 -30°，无任何自适应
26: mountConfig(mode=2, stabilize_roll=0, stabilize_yaw=0, stabilize_pitch=0)
33: msg.pitch = gimbal_pitch_               # 恒定值
36: mountCnt.publish(msg)
43: cam_pose_pub.publish(cam_pose)         # 只广播相机位姿，不参与控制
```
活系统实测：`/typhoon_h480_0/mavros/mount_control/command` **无数据** ✗（当前链路里云台未被驱动）

**发现**
| # | 问题 | 影响 |
|---|---|---|
| 1.1 | **云台俯仰固定 -30°，不是闭环朝向控制** | 目标近/远、高/低时相机指向不最优；目标远离光轴中心 → 检测框贴边 → 深度取样与三角化误差变大（与我们实测的 2.11 m 上报误差同源） |
| 1.2 | 稳定(`stabilize_*=0`)全部关闭 | 机体姿态扰动直接进画面，YOLO 框抖动 |
| 1.3 | 关节物理限位与官方不一致（`cgo3_camera_joint` 本地 `[-1.5708, 0.7854]` vs 官方 `[-1.05, 2.09]`） | 赛前合规风险（已在《模型合规》清单里） |
| 1.4 | 云台话题当前无发布者 | 深度/彩色画面实际由 SDF 固定安装角决定（与算法侧"pitch=0 但解算按 30°"的争议同源） |

**改进建议（按性价比）**
1. **闭环俯仰**：用目标在图像中的垂直偏移 + 目标深度估算所需俯仰角 `pitch = -atan2(h_cam - h_target, d_target)`，限幅在关节范围内，2~5 Hz 更新（不要 30 Hz，避免抖）；
2. **打开 roll/yaw 稳定**：`stabilize_roll=1, stabilize_yaw=1`，减少机体扰动进画面；
3. **对齐官方关节限位**（`[-1.05, 2.09]`），并把改动写进模型合规自查；
4. **保证云台指令话题有发布者**，否则"解算按 30°"这类外参争议无法闭环。

### 2.5 ✅ 已实施的改进（本轮）

**问题 2.1/2.2**：`simple_navigator` 是纯 P 律，只有全局 `MAX_SPEED_X=6 m/s` 上限；
接近航点时仍可能以高速冲入 `ARRIVAL_TOLERANCE=2 m` 圈，造成切角/超调。

**实施**（`src/mix_nav/simple_navigator/src/simple_navigator.cpp`，保留 `.orig_*` 备份）：

```cpp
// [zzu_fly 改进] 到点减速：进入 SLOW_RADIUS 后按 v <= SLOW_K*d 限速
const double SLOW_RADIUS = 8.0;   // m
const double SLOW_K      = 0.5;   // 1/s
double v_cap = MAX_SPEED_X_;
if (horizontal_distance < SLOW_RADIUS) v_cap = std::min(v_cap, SLOW_K * horizontal_distance);
if (vel_x >  v_cap) vel_x =  v_cap;
if (vel_x < -v_cap) vel_x = -v_cap;
```

效果：d=8 m 时限到 4.0 m/s、d=4 m 时 2.0 m/s、d=2 m（到点圈）时 1.0 m/s，
外部行为与原来一致（>8 m 不介入），风险低。**已通过 `catkin build simple_navigator` 编译验证** ✓

**证据**
```cpp
// ws2025/src/tracking/src/controller.cpp
15: Kp_pos_y 0.0025   16: Kd_pos_y 0.001       // 增益极小
17: Kp_yaw -0.0045    18: Kd_yaw -0.002        // 符号为负

```
活系统：`/typhoon_h480_0/tracking_node/yolo_human_tracking_*` 话题在但**当前无数据**（未进入跟踪）

**发现**
| # | 问题 | 影响 |
|---|---|---|
| 3.1 | 增益量级 1e-3、且 yaw 增益**为负**（正反馈风险） | 跟踪响应与符号需实测确认；若 PID 输出未按像素/高度归一，容易震荡或不收敛 |
| 3.2 | 跟踪控制器直接用**深度**做前后距离控制（算法侧已确认） | 深度无效/晚到 → 行为异常（我们实测过：无有效深度仍继续接近） |
| 3.3 | 无"深度失效"安全回退 | 冲过目标或撞目标 |
| 3.4 | 跟踪与上报**共用**同一目标判定，但上报只认 `detection.Class == active_tracking_id` | 类别名不匹配即静默不报（我们查出红人恒为 `red4` 的问题） |

**改进建议**
1. **归一化 PID**：误差用"像素/图像尺寸"或"目标相对角"表达，增益就能落在 O(1)，避免 1e-3 量级难调；
2. **深度门控**：`if depth invalid → 限速 0.3 m/s 或悬停`，绝不盲目前冲；
3. **上报与跟踪解耦**：上报只依赖"检测框 + 有效深度 + 坐标变换"，不依赖跟踪状态；
4. **类别映射表统一**（红人双发，见《红色映射缺陷》）。

2. **巡航高度降到 3.5~4 m**：低于 6 m 限高且提升检测质量；
3. 航点生成时**用 `black_box.txt` 做穿楼检查**（离线）；
4. 抽图后按实际 `base*.world` 自动选航线，而不是人工三类映射（已有 `map_generator` / `waypoint/view.py` 工具链可扩展）。

## 5. 无人机姿态控制（MAVROS setpoint / 模式切换）★当前阻塞点

**证据**
```
桥接 multirotor_communication.py:
 45: target_motion_pub = Publisher("<uav>/mavros/setpoint_raw/local", PositionTarget)
 50: armService        = ServiceProxy("<uav>/mavros/cmd/arming")

活系统实测（容器算法栈介入后）：
  /typhoon_h480_0/mavros/setpoint_raw/local  30.08 Hz ✓ 流未断
    coordinate_frame: 8      ← FRAME_BODY_NED
    type_mask: 1479          ← 忽略 P(XYZ)+AF(XYZ)+YAW，使用 V(XYZ)
    velocity.z: 1.5          ← 爬升指令
PX4 侧：
  INFO [commander] Armed by external command        ✓ 解锁成功
  INFO [commander] Disarmed by auto preflight disarming   ← 未起飞→自动上锁
  INFO [commander] Failsafe mode activated → RTL HOME
  WARN [PreFlightCheck] Mode not suitable for takeoff
结果：6 架全部 AUTO.RTL、未起飞
```
**发现**
| # | 问题 | 影响 |
|---|---|---|
| 5.1 | **PX4 未进入 OFFBOARD**（set_mode 返回 `mode_sent: True` 但模式未变）| 起飞流程第一步就失败 → HOVER 等待 → 超时自动上锁 → RTL |
| 5.2 | 失败保护后**无法再用 set_mode 恢复**（failsafe 期间 PX4 拒绝模式切换）⇒ 必须整轮重启 | 调试成本高 |
| 5.3 | setpoint 用 **BODY_NED(8)** 而非 LOCAL_NED(1) | PX4 1.13 对 offboard 首帧的坐标系/有效性更严格，需确认是否接受 body 系速度 setpoint |
| 5.4 | `COM_DISARM_PRFLT` 默认 10 s（我们已改 30 s） | 建立流/切换模式耗时 > 超时 ⇒ 必 RTL（**已修**） |
| 5.5 | 桥接无 setpoint **有效性自检**（NaN/超时/坐标系） | 失败无提示，只能靠 PX4 日志猜 |

**下一步动作（按技能"先证据链"原则）**
1. 新一轮**干净**启动后，逐条记录：`set_mode('OFFBOARD')` 返回值 → 1 s 后 `state.mode`；若仍不切换，
   把 setpoint 从 `FRAME_BODY_NED(8)` 换成 **`FRAME_LOCAL_NED(1)`** 再试（同时保留 30 Hz 流）；
2. 若仍失败，查 PX4 端 `[commander]`/`[mavros]` 关于 offboard 的拒绝原因（当前日志只有 `Mode not suitable for takeoff`）；
3. 给桥接加 **setpoint 自检**（发布前校验 NaN/坐标系/速率）并在失败的 1 s 内打印告警；
4. 记录"OFFBOARD→arm"与"arm→OFFBOARD"两种顺序的实测差异（PX4 对顺序敏感）。
