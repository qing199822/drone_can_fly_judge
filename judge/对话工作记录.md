## 1. 当前系统概览

当前工作空间已经形成一套本地单机仿真流程，主要包含：

- Gazebo 地图与人物模型仿真
- PX4 SITL 飞控仿真
- MAVROS 与 PX4 通信
- XTDrone 控制指令到 MAVROS 的桥接
- 航点导航和控制权切换
- YOLO11 行人检测（支持纯 CPU）
- RGB/深度图像到人物世界坐标的解算
- 无人机发现、追踪行人后返回航点导航
- 通过 ROS 速度话题控制 Gazebo 人物移动

当前启动流程明确按单架无人机配置。

```bash
GEOGRAPHICLIB_DATA="$WORKSPACE_DIR/geographiclib"
```

因此仿真可以直接使用工作空间中的 EGM96 数据，不必每次从国外源重新下载。

## 3. 仿真启动脚本

根目录的 `1.sh` 已从 Docker/tmux 六机脚本改为本地单机启动器，调用格式为：

```bash
bash ./1.sh [无人机数量] [任务文件] [sim|mission|full] [gui|headless] [地图]
```

不带参数时的默认值为：

```text
1 mission_down.json sim gui empty
```

参数含义如下：

| 参数 | 含义 |
| --- | --- |
| 无人机数量 | 当前只支持 `1` |
| 任务文件 | 例如 `mission_down.json` |
| `sim` | 只启动 Gazebo、PX4 SITL 和 MAVROS |
| `mission` | 在仿真基础上启动定位、起飞、导航、任务和跟踪节点 |
| `full` | 在 `mission` 基础上启动 YOLO 和深度坐标解算 |
| `gui` | 显示 Gazebo 图形界面 |
| `headless` | 只运行 Gazebo 服务端，不显示界面 |
| 地图 | `empty`、`base0` 至 `base16`，或一个 `.world` 文件路径 |

完整任务推荐使用：

```bash
cd ~/2025_ZZU_FLY
bash ./1.sh 1 mission_down.json full gui base0
```

`1.sh` 还会执行以下工作：

- 自动加载 ROS、工作空间和 PX4 Gazebo 环境
- 检查关键文件及 ROS 包
- 检查 Gazebo、MAVROS和人物话题是否就绪
- 避免重复启动已经运行的仿真
- 临时建立 PX4 自定义模型和六旋翼 airframe 链接
- 按 `Ctrl-C` 时清理由本脚本启动的进程及临时链接

## 6. 起飞、导航与控制权切换

起飞、航点导航和目标跟踪分别使用 MUX 输入：

- 起飞节点首先选择 takeoff 输入
- 起飞完成后切换到 navigator 输入
- 发现人物并进入跟踪时切换到 external 输入
- 跟踪会话结束后切回 navigator 输入

同时减少了 `simple_navigator.cpp` 中重复输出目标信息的问题。

这种设计保证目标跟踪只是暂时接管无人机，不会永久中断原航点任务。

## 8. 人物移动插件

相关文件包括：

- `src/gazebo_ros_actor_plugin/gazebo_ros_actor_cmd_plugin/include/actor_plugin_ros/ActorPluginRos.hpp`
- `src/gazebo_ros_actor_plugin/gazebo_ros_actor_cmd_plugin/src/ActorPluginRos.cpp`
- 对应的 `CMakeLists.txt` 和 `package.xml`

插件保留了原有的目标点指令：

```text
/actor_N/cmd_motion
```

同时新增人物速度话题：

```text
/actor_N/cmd_vel
```

消息类型为 `geometry_msgs/Twist`，其中 `linear.x` 和 `linear.y` 表示世界坐标系中的二维速度。插件会：

- 将速度大小限制在不超过 2 m/s
- 连续 0.5 秒未收到新速度命令时自动停止
- 持续维护人物的当前位置
- 到达目标或停止后保持当前位置，不再瞬移回出生点
- 根据人物实际移动距离推进步行动画

检测名称和人物模型的对应关系为：

| 检测名称 | Gazebo 人物 |
| --- | --- |
| `green0` | `actor_0` |
| `blue1` | `actor_1` |
| `brown2` | `actor_2` |
| `white3` | `actor_3` |
| `red4` | `actor_4` |
| `red5` | `actor_5` |

## 9. 发现行人后的逃逸与跟踪时限

相关文件包括：

- `src/tracking/src/state_machine.cpp`
- `src/tracking/include/tracking/state_machine.h`
- `src/tracking/config/params.yaml`
- `src/tracking/include/tracking/service_manager.h`
- `src/tracking/src/service_manager.cpp`

当前参数为：

```yaml
state_machine:
  max_tracking_duration: 10.0

actor_motion:
  duration: 3.0
  min_speed: 1.0
  max_speed: 2.0
```

当前行为如下：

1. 无人机首次锁定一个人物时，为人物生成随机二维方向和 1 至 2 m/s 的速度。
2. 以约 30 Hz 向相应的 `/actor_N/cmd_vel` 发布速度，持续 3 秒。
3. 3 秒后向人物发布零速度，使人物停在当前位置。
4. 无人机对同一个人物的整个跟踪会话最长持续 10 秒。
5. `DASH`、`TRACKING`、短暂丢失和重新捕获不会重置这 10 秒计时。
6. 10 秒到期后，MUX 控制权切回 navigator，并发布 `RESUME`。
7. 释放当前人物锁，把已完成目标加入集合，避免立即重复跟踪同一人物。

跟踪服务消息依赖也从废弃的 `serve_msg` 改为当前使用的 `look_up`。

## 13. 已知问题与注意事项

### 13.1 深度无效警告

以下警告来自 `src/yolo/bbox2coord_node.py`：

```text
无法获取 'green0' 在 (322, 268) 的有效深度。
```

该节点会在检测框中心周围读取 5x5 深度区域，并过滤小于等于 0 或非有限的深度值。当这一区域没有有效深度时，会跳过这一帧的人物世界坐标发布。

这表示 YOLO 已识别到人物，但相应深度像素无效，不代表 YOLO 或整个跟踪流程必然失败。常见原因包括：

- 检测框中心落在人物模型透明区域或深度空洞上
- 彩色图和深度图没有严格对齐
- 人物距离、遮挡或摄像机视角导致深度无效

本次工作尚未修改这一深度取值算法。

### 13.2 CPU 性能

当前 CUDA/GPU 不可用，YOLO 和 Gazebo 图形界面都可以使用 CPU，但帧率和识别速度会低于 GPU 环境。性能不足时可使用 `headless` 模式，或降低图像处理频率及分辨率。

### 13.3 检测框显示

系统目前发布检测结果消息和人物坐标，没有实现独立的检测框可视化窗口。需要通过 ROS 话题确认检测结果。

### 13.4 单机限制

当前 `1.sh` 和控制链按单架无人机完成验证，多机模式尚未完成同等程度的端口、命名空间和控制权测试。
