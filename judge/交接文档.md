## 4. ⚠️ 坐标系（最重要的坑）

tf 树：
```
map (slam)  →  odom (slam_toolbox)  →  base_link (odom_broadcaster)  →  laser_2d (static, z=+0.2)
```

**核心事实**：
1. mavros 位姿的 frame_id 是 **"map"**（EKF 世界帧）；slam_toolbox 也输出一个 **"map"**（SLAM 地图帧）。**两者同名但不同帧**。
2. `odom_broadcaster` 把 mavros 位姿**原样**广播成 `odom→base_link`，所以 tf 树里的 **"odom" 帧 ≈ mavros ENU 世界帧**。
3. slam_toolbox 建图时把机器人锚在**地图原点**，因此 `map→odom` 有一个**大旋转**（实测约 **-127.6°**，即机器人初始航向的逆）。这就是地图相对世界帧"整体偏转"的来源——这是**固定偏移**，不是漂移。
4. `explore_node` 里所有前沿目标、手动航点都活在 **SLAM map 帧**；读机器人位姿必须用 `getMapPose()`（tf 查 `map→base_link`），**不能直接用 mavros 的 x/y/yaw**，否则航向错乱、无人机原地打转。

## 5. 核心实现要点

### 5.1 A*（`include/auto_explore/astar.hpp`）
- 8 邻接栅格、octile 启发式、防斜穿墙角（corner-cut）。
- `astar::Cell{int x,y}`、`astar::plan(grid,w,h,start,goal)`、`astar::pathCost(path)`。占用：0=可走，非 0=障碍。

### 5.2 探索逻辑（explore_node）
- 状态机：`TAKEOFF → EXPLORE → DONE`。
- 慢环（1Hz，`frontierCb`）：对 `/map` 做**前沿检测**（FREE 且 8 邻域含 UNKNOWN），取距无人机最近的自由前沿为目标（两遍搜索，先限前向半平面避免掉头抖动）。
- 快环（20Hz，`controlCb`）：读 `/scan` 分 36 扇区求最小距离 → **反应式避障**（目标方向安全则前进+转向，否则沿最大空档走，即沿墙/沿路效果）。全程定高。
- 无前沿连续 `idle_timeout`（15s）→ DONE → `HOVER` → `map_saver` 存图。

### 5.3 手动多点导航（A* 全局路径 + 快速航点飞行）
- rviz 点击「2D Nav Goal」→ `manualGoalCb` 把点（转 map 帧后）压入 FIFO 队列 `manual_goals_`。
- **不再直飞**：队头目标先用 A* 规划全局路径（`planPath`，**带障碍膨胀** `plan_inflation`=0.6m，路径离墙保持安全距离），再做 **string pulling 抽稀**（`simplifyPathToWaypoints`：从起点不断找"直线可见的最远路径点"，每段直线经 Bresenham 验证无碰撞），得到少量拐点航点 `manual_wps_`。
- **A* 填充窗口（2026-08-24 新增）**：`planPath` 在包含起点+终点的**填充窗口**上规划，窗口外（当前 /map 之外）视为可通行/未知。目标再远也能立刻出路径（实测首个航点 70m 外、地图仅 25×36m 时 `A* 192 cells -> 2 waypoints`），随地图增长每 1s 重规划修正，激光反应式层兜底。此前"目标出图 → A* 直接跳过 → 兜底直飞在建筑间乱转 → 航点超时"的问题已修复。
- **快速直线飞 + 激光兜底（不撞墙）**：`manualFlightControl`（20Hz）朝当前航点全速直飞（`max_lin_x`=2.5），但**航向始终由反应式避障决定**（`chooseHeading(cone=1)`：目标方向 ±1 扇区净空 > `safe_distance` 才直飞，否则转向最大空档）；前向净空 < `manual_brake_dist`（2.0m）即比例减速，< `robot_radius`+0.3 硬停。**雷达（10m 量程）已见障碍就绝不继续直冲**——A* 路径只新鲜到上次 /map 更新，激光才是实时真相。
- **重规划时机**：目标改变 / 每 `manual_replan_interval`（1s）/ **激光见障即请求**（前向净空 < 2.0m 置 `replan_requested_`，1Hz 规划器立刻重算 A*）→ 重算并 `rebaseWaypointIndex` 续飞。
- **到达/超时**：航点走完（或兜底直飞距离 < 0.5m）或 `manual_goal_timeout`（120s）→ 弹队头、进下一点；队列清空后回到自动前沿探索。
- **兜底**：A* 失败（地图未就绪/目标出图/不可达）时退回原来的直飞 + 反应式避障，随地图增长每 2s 自动重试进入 A* 模式。
- 探索模式的原纯追踪（沿 A* 栅格爬 + 保守避障）**保持不变**，只作用于前沿目标。

### 5.4 写死航点（本轮新增）
- 航点写在 `explore.launch` 的 `<rosparam param="waypoints">`（节点私有命名空间 `/explore_node/waypoints`），格式 `[[x,y], ...]`，**mavros ENU 坐标（相对出生点 (-17,-3)）**。
- ⚠️ **坐标系换算（重要踩坑，2026-08-24 实测确认）**：mavros `local_position/pose` 的 ENU 原点 = **无人机出生点 (-17,-3)**，不是 Gazebo 世界原点。三重证据：(1) 实测出生点处 mavros 位姿=(0.13,-0.03)≈(0,0)、home_position=(0,0)，而 Gazebo 世界系是 (-16.9,-3.0)；(2) `pose_init` 源码 `drone_offsets = {"typhoon_h480_0", {-17,-3,0}}`（local + offset = 世界系）；(3) PX4 sitl_gazebo 的 GPS 原点 = 世界 (0,0)，但 EKF 局部原点锚在首帧/出生点。所以 **ENU = 世界坐标 + (17, 3)**。`base0.world` 道路坐标是世界坐标，**不能直接搬进 launch**（旧 up 层 9 点和此前一版 middle 18 点都偏了 (17,3)——"航点给的不好/不对"的根因）。旧 task_manager 的 `mission_*.json` 是世界坐标，只在旧系统（pose_init 补偿）里才有效。
- `explore_node` 构造时读进 `preset_waypoints_`；在**首个 frontier 周期**（地图/tf 就绪后）用 `loadPresetWaypoints()` 把每个点从 `odom` 帧 tf 转到 `map` 帧再入队，然后按 §5.3 的 A* 方式执行。这样 `map↔odom` 的大旋转被 tf 自动消掉。
- 空列表 = 退回自动前沿探索。
- 写死航点与手动 rviz 目标走**同一条手动队列**，同样 A* + 抽稀 + 快速航点飞行（不再是点对点直飞）。

## 6. 建图漂移与自遮挡（已修复）

### 6.1 漂移：关扫描匹配、信任 odom

**症状**：地图随运动越来越扭曲、对不齐（注意与第 4 节"整体固定偏移"区分）。

**根因**：`use_scan_matching: true` 让 slam_toolbox 用「倾斜的 2D 扫描」（无人机俯仰/横滚导致）做扫描匹配、重新估位姿，覆盖 mavros 那条在仿真里本就零漂移的完美 odom，误差逐帧累积。

**已应用的修复**（`config/mapper_params_online_async.yaml`）：
```yaml
use_scan_matching: false       # 位姿直接用 mavros，不再扫描匹配
use_scan_barycenter: false     # 匹配已关，一并关掉
do_loop_closing: false         # 回环内部也走扫描匹配，会绕过主开关重新引入漂移
minimum_time_interval: 0.0     # 不丢帧，扫描全覆盖
```
效果：地图不再漂移（`map→odom` 的 -127.6° 大旋转仍是固定偏移，`getMapPose()` 逻辑不变）。

### 6.2 自遮挡：周身点云切割

**症状**：漂移修好后，地图里仍留下无人机自己飞过的轨迹（机身/桨叶进入扫描被当成障碍写进地图）。

**修复**：新增 `scan_self_filter_node`，在 SLAM 前把 `ranges < cut_radius`（默认 0.7m）的读数改成 `+inf`，发布到 `/<vehicle>/scan_filtered`；slam_toolbox 与 explore_node 都改吃过滤后的话题。

**为什么用 +inf**：karto 的 `OccupancyGrid::AddScan` 对 `>= maxRange`（或 NaN）的读数直接 `continue` 整条射线跳过——既不把机身标成 occupied，也不沿射线清 free，语义正好是"切割"。同时 `+inf > range_max`，explore_node 的 `buildSectors` 也会跳过，避障不再把自家桨叶当障碍。

**调参**：轨迹还在→`cut_radius` 调大（如 0.9）；近处真实障碍被切掉→调小。启动时 `roslaunch auto_explore auto_explore.launch cut_radius:=0.9`。

### 6.3 高速飞行建图模糊：倾斜补偿 + 地面剔除（2026-08-24 新增）

**症状**：手动快速航点飞行时（`max_lin_x`=2.5、`manual_max_yaw_rate`=0.8），rviz 里地图几乎空白、墙体变散点。

**根因**：2D 激光装在机体上，高速飞行持续俯仰 **10~18°**（实测）。倾斜扫描平面导致：(1) 墙面距离被拉长 `1/cos(18°)≈5%`，墙体发虚；(2) 前下方射线打到**地面**形成随行的假墙环；(3) 扫描面贴着屋顶边缘/灯杆高度扫，产生大量散点。低速探索时俯仰小（<5°）所以之前的图还行，快速飞行放大了问题。

**修复**（`scan_self_filter.cpp` 增强，随 scan 一起生效）：
- **倾斜补偿**：用 mavros 姿态（roll/pitch）把每条射线投影回水平面，`range' = range × |射线水平分量|`（实测补偿比 0.935 ≈ cos(19°)，墙距误差归零）。
- **地面剔除**：射线向下且 `竖直下落 ≈ 激光离地高度`（`pose_z + laser_z_offset + ground_alt_offset`，容差 `ground_margin`=0.8m）→ 判为地面命中改 `+inf`。
- 参数：`pose_topic`（默认 `/typhoon_h480_0/mavros/local_position/pose`）、`laser_z_offset`=0.2、`ground_alt_offset`=1.0（EKF 原点高于地面 1m，即出生点 z=1）、`ground_margin`=0.8。
- **注意**：`ground_alt_offset` 依赖"地面在 EKF 系 z=-1"，换地图/改 spawn z 时按需调整；若地面环仍在→调大 `ground_margin`；远处真实低障碍被误删→调小。

**仍可选的辅助手段**（补偿后通常已不需要）：降速（`max_lin_x` 1.5、`k_lin` 0.5）、提高 `target_altitude`（5m，让地面环超出 10m 量程）。

### 6.4 建图空/散点：雷达高度 + 量程 + 膨胀（2026-08-24 二次修复）

**症状**：快速航点飞行时 rviz 地图几乎空白（未知 97%+）、墙体散点不成线、每帧有效激光仅 15 条。

**根因（实测逐帧分析）**：
1. **机身自遮挡**：雷达装在 z=0.2，机身碰撞体（0.67×0.67×0.15，顶面 z=0.075）只低 12.5cm，飞行俯仰 ≥15° 时机身四角切入扫描面，形成 0.34~0.43m 的 360° 自遮挡环——每帧 73~229 条有效射线被砍，只剩 15 条墙线。
2. **量程 10m**：一次只扫 ~20m 宽走廊，大片区域保持未知。
3. **A* 膨胀 0.6m**：真实障碍仅占 0.25% 时膨胀后占 32.5%，楼间缝隙全堵死 → A* no path → 兜底盲飞撞楼坠机。

**修复（4 处）**：

### 6.7 无人机"卡在墙旁边"根因与修复（2026-08-26 晚 → 08-27 凌晨，headless 6 机验证通过）

**用户现象**：有无人机卡在墙边不动/贴地。排查结论：**不是航点设置问题**（航点都在道路交叉口，坐标换算已验证），而是低矮障碍撞机 + 转移直飞逻辑缺陷。

**根因（证据链）**：
1. **低矮障碍是 lidar 盲区**：5.5m 飞行 + 0.6m 安装 = lidar 平面约 6.1m。`base0.world` 中 `house_1`（高 5.12m，world 里 scale 1.5 与 1.0 重复定义，Gazebo 后者生效）、`fast_food`（高 5.54m）、`dumpster`（高 2.62m）等在融合地图上**不产生占用** → A* 认为可通行 → 撞墙。实测 drone2 卡在 `house_3_158`(-25.7,-19.4) 旁、drone5 坠在 `fast_food_93`(28.3,-13.9) 旁（直线路径恰好穿过它，5.54m 高 ≈ 飞行高度 5.5m，差 0.6m 就是扫不到与撞上的临界）。
2. **撞墙后 PX4 disarm 无法恢复**：撞机 → 碰撞检测 disarm → EKF 高度发散（mavros z=-317/-200 假读数）→ pre-arm 检查失败 → 持续 "FCU rejected arm request" → 永久卡死。
3. **transfer_dist=60m 直飞无条件清空 A***：远处目标直飞穿过建筑群撞墙；且直飞段被 manualFlightControl 当"无路径"→ 压到 0.8m/s 爬行 + 20s 误触发回溯 → 原地振荡。

**方案演进（重要）**：
- 第一版尝试 **先验障碍烘焙**（`scan_map_fuser` 的 `loadPriorObstacles()`：从 `base0.world` 解析建筑坐标尺寸写入 `/map`，`prior_` 掩码防 clearLine 擦除，实测烘焙 24.6 万格）——**但用户指出"这样建出来的图不对"**：地图必须由传感器真实扫描，烘焙 = 预知地图，比赛不允许时就是作弊，且尺寸是估算的有偏差。**已整体撤销**（`loadPriorObstacles`/`prior_`/clearLine 保护全部删除，地图 100% 纯激光扫描）。
- 最终采用**物理解法：降低飞行高度**，让 lidar 平面低于所有会撞的障碍。

**障碍高度分析（base0.world 全量提取，dae 网格英寸→米 × scale）**：
| 高度区间 | 障碍 | 结论 |
|---|---|---|
| <2m | 消防栓/停车牌 1m、托盘 0.04m 等 21 个 | 低于飞行高度，**飞越不撞**，无需扫到 |
| 2-4m | dumpster 2.62m | 低于飞行高度 4.0m，**飞越不撞** |
| 4-5m | **无任何障碍** | 安全区间，飞行高度取 4.0m 的关键 |
| 5-6.1m | house_1 5.12m、fast_food 5.54m | **会撞**，必须扫到 → 4.0m 飞行 + 0.6m 安装 = lidar 平面 4.6m < 5.12m ✓ |
| >6.1m | house_3 7.07m、加油站 7.65m、路灯 10.5m、house_2 14.9m | 一直能扫到，绕行 |

**修复（全部实测）**：
| 问题 | 修复 |
|---|---|
| 低矮障碍是 lidar 盲区（根本） | **飞行/转移高度 5.5m → 4.0m**（`auto_explore_swarm.launch`）：lidar 平面 4.6m，能真实扫到所有会撞的障碍（house_1 5.12m / fast_food 5.54m / house_3 7.07m 等）；4~5m 区间无障碍保证安全；dumpster 2.62m 等矮障碍低于飞行高度可飞越。**地图纯扫描，无烘焙**。 |
| 起飞首段地图全 unknown，直飞盲穿建筑群（drone2 撞 house_3、drone5 撞 fast_food） | **`manual_waypoints_flown_==0`（还没到过任何航点）时禁用 TRANSFER 直飞**，强制走 A*（随地图增长 1Hz 重规划，接近后障碍被扫到即绕行）。 |
| 刹车公式失效：`k_lin_*(fwd-r)` 在 fwd=15m 时算出 8.6m/s 被 2.5m/s 上限 clamp，实际到 4.8m 才减速，来不及 | **渐进式提前刹车**：fwd<15m 时线性降速 `0.5 + 2.0*(fwd-2)/(15-2)`（15m 处 ~2.5m/s → 2m 处 ~0.5m/s）；A* 航点模式同样适用；replan 触发距离 A* 模式提到 10m。 |

| gzserver libprotobuf 偶发 segfault（exit 139，spawn 完成后高频） | `spawn_drones.launch` 错峰间隔拉大：`spawn_delay=8+5*id`（8~33s）、`sitl_delay=15+4*id`（15~35s）；1.sh 监控循环自动重启（重启会换 rosmaster，swarm 需重启 swarm 节点重连）。 |

**验证结果（headless，6 机，全程 0 超时 0 回溯，master 稳定 ~7 分钟）**：
- drone0/1/2：各自 2/2 航点全部到达；drone3/4/5：4/4 全部到达。
- **drone2 首段成功穿越 house_3 建筑群、drone5 首段绕过 fast_food**（此前反复撞墙的机）。
- 全部 6 机高度 3.7-4.6m（< 6m 限高），沿路巡逻，无坠机、无 disarm。

## 7.5 MPPI/安全层 P0 修复

针对长时间测试中出现的停滞、坠落和控制状态不一致，本轮补充了以下保护：

- MPPI 每周期使用当前控制速度作为 nominal，不再盲目使用旧 warm-start；外部安全层后的状态可重置 warm-start。
- `LaserScan` 无效、全无效、非法量程或没有足够有效回波时，MPPI 标记为 invalid，任务节点立即停车，不再把空扫描当作无障碍环境。
- `range_max`/无回波值不再作为障碍点写入距离场。
- 深度急停、TTC 急停、位姿跳变、飞行中异常低高度均绕过平滑器并直接清零水平/偏航速度；起飞阶段允许从地面高度正常起飞。
- ROAD 和 PATROL 的 MPPI 采样预算均为 `100×16`；ROAD 使用独立规划器，`road_mppi_v_des=3.5`、`road_mppi_max_v=5.0`，PATROL 使用 `v_des=1.5`、`max_v=2.0`，避免不同阶段的速度目标互相覆盖。
- ROAD 视觉横向误差转换为 FLU 机体系时取反，避免图像右侧道路产生错误的左移命令。

这些改动已完成编译、道路合成测试、握手协议测试和 launch 静态检查。Gazebo 的 `libprotobuf.so.17` 原生段错误仍是独立环境阻塞，完整六机长时间回归需在 Gazebo 稳定后重新进行。


ROAD 阶段现在也使用 MPPI：道路视觉结果只作为局部道路方向先验，最终目标方向和过滤后的激光障碍距离场共同进入 MPPI；深度/激光急停与主动绕障仍在 MPPI 输出之后执行。MPPI 默认采样数从 300 降到 100、预测步数从 24 降到 16，降低六机 CPU 负载。

区域任务增加异常位姿/高度保护：局部位姿单次跳变超过 4 m 或高度低于 1 m 时停止水平和垂直运动并输出错误日志，避免 EKF 发散数据继续驱动控制。六机模型生成错峰改为 `spawn_delay=8+5*id`、`sitl_delay=15+4*id`，用于缓解 Gazebo 多模型初始化时的 `libprotobuf.so.17` 段错误。

本轮静态/编译测试通过；短时 headless 回归被环境已有的 Gazebo/Protobuf 原生段错误阻断，未将其伪称为飞行通过。


道路视觉节点现在订阅每架无人机的 `mavros/local_position/pose`，读取 roll/pitch 并动态调整图像 ROI；姿态变化时道路中心偏差也做滚转补偿。道路短时丢失时默认保持上一帧结果 0.6 s，并衰减置信度，不再单帧失败立即把前进速度清零。

- 道路视觉现在使用 YOLO 语义分割 mask，不再依赖道路颜色、亮度或 OpenCV 阈值；道路候选由分割 mask 的连通方向和宽度提取。

## 7.1 视觉道路跟随（当前版本）

ROAD 阶段已不再使用固定的中间道路航点。每架无人机启动一个 `road_follow.py`，订阅自己的 RGB 相机话题 `/typhoon_h480_<id>/realsense/depth_camera/color/image_raw`，在下方 ROI 中估计道路候选区域的中心偏差、道路方向和置信度，并通过 `/typhoon_h480_<id>/road_follow/steering` 发布 `geometry_msgs/Vector3`：`x=横向偏差`、`y=方向偏差`、`z=置信度`。

`area_mission_node` 在 ROAD 阶段以视觉结果作为道路方向先验，并由 ROAD-MPPI 综合目标方向与激光距离场生成指令；当前位置到最终区域目标的 GPS/EKF 距离仍用于目标到达判定，六机 launch 的 `wp_reach_tolerance` 统一为 10 m。距离最终目标不超过 `road_approach_distance`（默认 20 m）后，ROAD-MPPI 的目标方向显式以最终目标为主（默认 80% 目标方向、最多 20% 道路先验），因此可以离开不通向航点的道路；远距离 ROAD 行为保持道路巡航。候选组 `[heading_norm,lateral_norm,confidence,width]` 按候选方向与当前目标方向的夹角、置信度、宽度和横向偏差评分；切换须满足 `road_candidate_switch_margin` 且连续 `road_candidate_confirm_cycles` 个控制周期，避免路口左右振荡。道路方向暂时不一致时继续保留道路先验；道路暂时丢失或 hold 超时后使用有界、低速的目标方向 MPPI 接近，不再无限原地旋转。深度相机和激光雷达仍是最终防撞层。

ROAD 还按 `progress_window` 窗口监测目标距离：单窗口至少减少 `minimum_progress` 才算有效，临时绕障造成的短时增距会被容忍；连续 `progress_bad_windows` 个坏窗口，或距离增加超过 `wrong_branch_distance`，进入有界 `road_recovery_duration` hold/search 状态，停止前进、原地搜索并重置距离基线，不会盲飞穿楼。参数默认分别为 8.0 s、1.5 m、5.0 m、2 个窗口和 5.0 s。暂停/追踪返回期间不更新该监测器，避免干扰 PATROL/TRACKING。

当前道路检测使用 Ultralytics YOLO 语义分割，默认权重为 `/home/lishu2/2025_ZZU_FLY/best2.pt`。`auto_explore_swarm.launch` 通过 `road_model`、`road_class`、`infer_imgsz`、`infer_conf`、`infer_iou`、`infer_device` 和 `infer_max_det` 参数将模型及推理配置传给全部六个 `road_follow_gpu.sh` 节点。该启动器使用现有 `~/miniconda3/envs/yolo_gpu`（torch cu128），补齐 ROS/devel 的 `PYTHONPATH` 和环境的 `LD_LIBRARY_PATH` 后执行 `road_follow.py`；默认 `infer_device` 为 `cuda:0`，仍可显式传 `infer_device:=cpu`。分割 mask 的几何特征转换为原有 Vector3/candidates 接口；道路视觉调试图仍发布在 `/typhoon_h480_<id>/road_follow/debug_image`。

## 12. 六机启动稳定性：严格串行门控启动链（2026-09-14 新增）

### 12.1 背景：为什么先解决启动，而不是先调算法

长时间排查的结论是：**"无人机不动"不是单个导航算法问题，而是启动层多问题叠加**。
在 Gazebo/PX4/MAVROS 未稳定前，导航不动、位姿异常、激光过期、MPPI 清零都不能作为算法结论。
因此本轮把优先级放在"六机 Gazebo/PX4/MAVROS 启动稳定性"上。

先澄清三条**曾被怀疑、实际已不存在**的问题（本轮逐项核实）：

| 曾怀疑的问题 | 核实结果 |
|---|---|
| MAVLink 端口重复（QGC 都用 14550） | **已修复**：六机 QGC=14550+id、sdk=14540+id、mavlink tcp=4560+id、udp=18570+id、gimbal=13030+id，全部唯一 |
| PX4 / SDF / Gazebo 插件路径混用（两个 PX4 目录） | **不存在**：`/home/lishu2/PX4_Firmware` 是指向 `/home/lishu2/PX4-Autopilot` 的软链；模型目录 `.../models/typhoon_h480_zzufly` 是指向工作空间 `typhoon_h480_zzufly/` 的软链，**单一来源** |
| 模型并行生成 + PX4 早于模型启动 | **确实存在**（本轮修复，见下） |

### 12.2 旧的启动时序（问题所在）

`1.sh` → `roslaunch robocup_zzufly.launch` 一次性展开：
Gazebo + N 个模型生成（仅用 `spawn_delay=5+12*id` 时间错峰）+ N 个 PX4（`wait_for_model.py` 只等"自己的模型出现+3s"）+ N 个 MAVROS，**全部并行**。
后果：PX4 可能早于模型完成而等待 TCP 4560+i；六个大 SDF 同时请求生成会阻塞 Gazebo 生成服务；负载与时序不稳定（`bind failed`、生成超时、gzserver exit 139）。

### 12.3 启动模式与门控

编排器有两档模式（`STARTUP_MODE`）：

- **`batch`（默认，快）**：串行生成 + 错峰并发启动，见 §12.3.1；6 机实测 **12s**（§12.6）。
- **`serial`（最保守）**：逐架 spawn→确认→PX4→等 connected 才动下一架；6 机约 30~35s，用于
  需要极致时序控制的排查（例如怀疑"上一架 connected 前启动下一架会出问题"时）。

两档模式都保留同样的关键保证：**世界就绪后才生成模型**、**每个模型确认存在后才启动它自己的 PX4**、
**全部 connected + 健康门通过后才启动上层算法栈**、**生成请求一次只发一个**（避免压住 Gazebo 生成服务）。

#### 12.3.1 batch 模式的四步

```
① 串行生成 + 逐个确认模型（0..N-1，每架 ~0.35s，仍是一次一个请求）
② 按 drone 顺序错峰启动 PX4 + MAVROS（PX4_STAGGER，默认 0.5s）
③ 用订阅缓存并发等待"全部 connected=True + 位姿可用"（只受一个总 deadline 限制）
④ 控制桥 → 健康门（模型/位姿/激光/端口冲突分级）→ 通过才放行上层
```

> 时间都花在哪：串行模式每架要等 PX4 启动完（~3.4s）才动下一架，6 架 ≈ 20s+；
> batch 把这段"等 PX4"重叠掉，只保留 0.5s 错峰，因此 6 架的 PX4 启动≈并行，
> 总耗时 ≈ 世界加载 + 6×0.35s(生成) + 6×0.5s(错峰) + max(PX4 启动≈3s) + 健康门。

#### 12.3.2 serial 模式的原始时序

```
启动 Gazebo（仅世界，robocup_zzufly_gazebo.launch）
   ↓ 等 /gazebo/get_world_properties 可用且模型数稳定（最多 600s，每 20s 打印进度）
   ↓ 调 /gazebo/unpause_physics 确认未暂停
for drone i in 起始id .. 起始id+N-1:                    ← 上一架未通过就不启动下一架
   ├─ spawn_sdf_model（阻塞式服务调用，模型 i）
   ├─ get_model_properties 轮询确认模型真的在 Gazebo 里（最多 300s）
   ├─ 启动 PX4 SITL(instance i)（PX4_SIM_MODEL/PX4_ESTIMATOR，日志 logs/serial_bringup/px4_i.log）
   ├─ 启动 MAVROS(i)（mavros_vehicle.launch，fcu_url=udp://:1454i@localhost:1458i）
   └─ 等 /typhoon_h480_i/mavros/state connected=True 且位姿话题有数据（最多 120s）
   ↓ 六架全部就绪
启动 xtdrone 控制桥（cmd_vel_flu → MAVROS）
   ↓
健康门检查 → 通过才允许 1.sh 启动上层算法栈（否则以非 0 退出，拒绝启动）
```

上层栈启动顺序也按期分层（`sim` 模式）：
**阶段 A** 静态 TF / pose_init / transform_tree / MUX / lookup →
**阶段 B** `auto_explore_swarm`（激光过滤 + TF + 区域任务）→ 等 `wait_for_upper_stack_ready`
（`scan_filtered` + `/map` + `tf map→base_link_<id>` 全部可用，最多 180s）→
**阶段 C** YOLO（道路分割 + 行人检测）/ 坐标解算 / 云台 / tracking。
视觉与追踪属重负载，**激光过滤与 TF 不健康就不启动**，避免把底层问题误判成算法问题。

### 12.5 健康门判定（重要：不要把良性告警当失败）

**致命（FAIL）**：模型不在 Gazebo、PX4 进程退出、MAVROS 未连接、位姿话题无数据、
位姿 z 异常（|z|>50，疑似 EKF 发散）、原始激光无数据、gzserver 不在运行、
**本机 offboard 端口 14580+id 绑定失败**。

**仅告警（WARN）**：原始激光有效点少（空世界/开阔地属正常）、
**其他 mavlink 端口绑定失败**。

> ⚠️ **14558 端口告警是良性的，不要据此判失败**：
> airframe `6011_typhoon_h480.post` 里写死了 `mavlink start -x -u 14558 -r 4000 -f -m onboard -o 14530`，
> 六个实例都会尝试绑 14558，只有第一架能成功，其余都会打印
> `WARN [mavlink] bind failed: Address already in use`。
> 导航依赖的是 offboard 端口（14580+id），`connected=True` 已证明主链路可用。
> 判据实现见 `analyze_mavlink_binds()`：按 PX4 日志"`on udp port P` 行后紧跟 `bind failed`"配对定位端口，
> 只对本机 offboard 端口判致命。

### 12.6 本轮实测结论（2026-09-14）

**已完成**：`1.sh` / 编排器 / launch 语法检查、`catkin build xtdrone_mavros_bridge`、
7 项编排器逻辑回归测试 + 2 项上层健康门回归测试全部通过；并在隔离环境（可写 HOME、
`DISPLAY` 留空让 Gazebo 关闭渲染、独立 ROS master）用 **真实 base0 + 真实 PX4/MAVROS** 做了端到端验证：

| 项目 | 结果 |
|---|---|
| Gazebo 世界就绪门控 | base0 加载 **91 个模型耗时 4s**；`unpause_physics` 调用成功 |
| 严格串行（`serial`）spawn→确认→PX4→MAVROS | 单架 **4.7~5.8s**（模型生成 0.3~0.4s，PX4→connected 3.3~3.4s）；2 机、4 机均逐架通过 |
| **batch 模式（新默认，目标 30s 内）** | **4 机 10s**、**6 机 12s**（世界加载 2.0s + batch 启动 8.5s + 健康门 ~1.5s），6/6 `connected=True`、`AUTO.LOITER`；6 机 batch 运行存活约 5 分钟未复现 139 |
| 健康门 | 每架 `模型✓ 位姿✓ 激光✓`（base0 有效激光点 78~101）；仅良性 WARN(14558) → 通过 |
| 稳态 | 编排器退出后 75s：PX4/MAVROS/gzserver 全部存活；`connected=True`、`mode=AUTO.LOITER`、位姿持续更新 |
| 上层健康门 | 假发布者注入 `scan_filtered`/`/map`/静态 TF → 检查器退出码 0；停掉发布者 → 退出码 2（不假通过） |
| 失败快速中止 | 任一环节失败 → 编排器非 0 → `1.sh` 拒绝启动 YOLO/tracking |

**修掉的一个真 bug（重要）**：编排器最初在正常退出时也会执行"清理子进程"，导致健康门通过后
**PX4/MAVROS 被悄悄杀掉**（而 `1.sh` 只监控 gzserver，不会报错）——现象正是"无人机不动"。
现在只有**失败中止或收到信号**才回收子进程，正常退出保留底层；已用"编排器退出后 75s 仍存活"验证。

**本轮发现但未解决（这才是当前真正的阻塞）**：4 机 base0 跑到稳态后，gzserver 仍会
**Segmentation fault (core dumped) → exit code 139**。关键时间线表明它**发生在启动完成之后**
（`六机底层启动通过` → `基础仿真已就绪` → 数秒后段错误），因此：

- **不是**模型并行生成/时序问题（串行化后单架生成仅 0.3~0.4s，4 机全部成功插入并 connected）；
- 属于 `libprotobuf.so.17` 的运行时崩溃（与 §9.7 同一问题），与 §12.8 的观察一致。

目前的现象（样本仍少，只能作为线索）：**崩不崩与"规模 × 上层负载"相关**——

| 运行 | 机数 | 辅助节点 | 结果 |
|---|---|---|---|
| F（serial） | 4 | 开 | 稳态后数秒 exit 139 |
| G（serial） | 4 | 关 | 存活 2.5 分钟以上，未复现 |
| **J（batch，新默认）** | **6** | **关** | **存活约 5 分钟，未复现；6/6 connected=True** |
| E（serial） | 2 | 开 | 90s 内未复现（人为结束） |

即：机数多 + 上层节点同时压上来时更容易崩，符合 `libprotobuf` 运行时崩溃的负载相关性。
下一步按 §12.6.1 用 A/B/C/D 逐步放开负载，定位是**哪个节点**把 gzserver 推过临界点。

**未在本环境验证**（必须在带 GPU 的正常机器上跑）：相机相关（YOLO 道路分割/行人检测、
tracking 接管）、六机长时间飞行、MPPI/区域任务/到达判定等算法层结论。
本轮只声明"底层启动链"的结论。

### 12.6.1 定位 139 的建议二分步骤

```bash

# C) 再开建图/区域任务（阶段 B）
START_SIM_HELPERS=1 START_PERCEPTION=0 AUTO_EXPLORE_SWARM=1 \

# D) 最后开感知/追踪（阶段 C）

```
每一步记录"从稳态到崩溃的秒数"和 `logs/serial_bringup/health_report.json`；

### 12.8 仍存在的限制

1. `~/.ros/log` 或 `~/.gazebo` 不可写时（只读挂载/受限容器）rosmaster 会直接退出；
   本轮已在 `1.sh` 里加 `ROS_LOG_DIR` 回退到 `logs/ros`，但 `~/.gazebo` 只读仍会导致
   gzserver 世界加载卡死，需要可写 HOME（正常机器不受影响）。
2. Gazebo 渲染需要可用 GLX：无 GLX 的 X 服务器会打不开渲染；
   把 `DISPLAY` 留空可让 Gazebo 以"渲染关闭"模式继续跑（激光是物理射线，仍可用，相机不可用），
   这只适合底层排查，正式任务必须用带 GPU 的正常显示环境。
3. Gazebo `libprotobuf.so.17` 段错误**仍未根治**：串行化已消除"生成期"并发压力
   （4 机模型 0.3~0.4s 全部成功插入），但实测 4 机 base0 在**稳态后**仍会 exit 139。
   定位建议见 §12.6.1，不要把它误判成导航/算法问题。

5. 编排器在**失败/收到信号**时会回收自己启动的 PX4/MAVROS；**正常退出**会保留它们，

## 13. ROAD 阶段"原地旋转 / 几乎不前进"修复（2026-09-14）

### 13.1 现象与证据（用户实测，2~5 号为主）

| 观测 | 值 |
|---|---|
| 道路分割 | `accepted=1`、`yolo_conf≈0.92~0.97`、`pass_min/usable/bottom/near_far=1`、`heading_available=1` |
| 激光 | 原始/过滤均 ~50Hz 更新（有效点 80~255） |
| 最终速度 | 2 号 `v≈0`；3 号 `v≈0.02~0.05`；4 号 `v≈0`；5 号 `v≈0` 且 `w` 在 ±0.8 rad/s 摆动 |
| 其它 | 5 号 `ROAD selected branch` 频繁切换；出现 `ROAD stalled; crawling recovery`；2 号曾 `scan stale; holding motion` |

结论（与用户判断一致）：**YOLO/后处理没问题，是 ROAD-MPPI + 安全层把前向速度压到 ≈0 却保留偏航**。

### 13.2 根因（本轮补充的定量证据）

1. **ROAD 沿用了 PATROL 的保守代价**：`mppi_obstacle_weight=80.0`、`mppi_safe_radius=4.0`
   （动态安全半径 `max(safe_radius, 0.8v)`，v 小时仍 4m）⇒ 只要激光点在 4m 内，
   所有"向前"的 rollout 都带巨额惩罚，而"停住/旋转"代价低（`yaw_weight` 只有 0.05）。
2. **低速是自增强死锁**：MPPI 以当前平滑速度 `smooth_x_` 为 nominal（warm start），
   一旦进入低速，采样分布在低速区、速度项 `(v-v_des)²` 也难把它拉回来，
   于是长期停在 `v≈0.1、w≈1.1`（贴墙旋转）。
   反之如果一开始就有速度，MPPI 自己就会选择前进——所以同一套保守代价，**能否起步是双稳态的**。
3. `road_mppi_min_v=0.0` 让 `v=0、w≠0` 成为合法最优解；`updateRoadProgress` 只在
   `|cmd.linear.x|≥0.2` 时才计时，于是"卡住"时连 stalled 恢复都不会触发，形成互相掩护。

### 13.3 四项修复

| # | 修复 | 实现 | 参数（config/area_mission_road.yaml） |
|---|---|---|---|
| ① | **ROAD 前进速度下限** | 安全层之后、区域边界之前兜底；硬停路径（深度急停/TTC/激光无效/MPPI 无效/位姿异常）在到达该处前已 `break`，不受影响；crawl recovery、道路保持、近目标段跳过；要求**前向净空 > 下限净空**才兜底 | `road_min_speed_floor=1.0`、`road_min_speed_floor_clearance=3.0` |
| ② | **道路方向稳定** | `chooseRoadGuidance` 出来的方向做 EMA 低通 + 单周期限幅（视觉丢失即重置，恢复时立刻响应）；分支切换滞回与确认周期加大 | `road_guidance_filter_alpha=0.25`、`road_guidance_max_step=0.05`、`road_candidate_switch_margin=0.35`（原 0.18）、`road_candidate_confirm_cycles=25`（原 15） |

### 13.6 ⚠️ 运维坑：`rosrun _param:=` 会残留在参数服务器

本轮排查中一度出现"新参数跑出旧行为"：`rosrun ... _road_mppi_obstacle_weight:=80.0`
设的是**参数服务器上的私有参数**（`/typhoon_h480_0/area_mission_node/...`），
**节点退出后不会自动清除**；下一次运行即使不传该参数，读取到的仍是残留值，
而 `pnh_.param(key, default)` 只在参数不存在时才用默认值。

- 排查任何"参数改了没效果"时，先 `rosparam get /typhoon_h480_0/area_mission_node/<key>` 核对；
- 清残留：`rosparam delete /typhoon_h480_0/area_mission_node`（或重启 master）；
- 正式跑用 launch 时，launch/YAML 里显式写入的值会覆盖残留，但**YAML 里没有的键仍可能被残留值顶掉**。

### 13.8 诊断可达性 + scan stale 误判修复（2026-09-14 二次跟进）

#### 为什么上一轮"读不到 diag"

初版诊断是从控制路径里、按 **ROS 时间**限速发布的，有三个致命点：

1. 控制路径早退/`break` 时不发（想排查的时刻恰恰是它不动的时候）；
2. 用 `ros::Time` 限速 + `ros::Timer` 发布 —— **仿真时钟停走/跳变时（Gazebo 暂停、/clock 抖动）
   ROS 定时器会一起冻结，一条都发不出来**；
3. 没有 latch，`rostopic echo` 晚起就什么都抓不到。

#### 现在给你的五重保险

| 保险 | 实现 | 好处 |
|---|---|---|
| ① 独立**墙钟**定时器 | `createWallTimer(1/diag_rate)` → `publishDiag()` | 仿真时钟冻结/跳变时诊断照常更新 |
| ② **latch=true** | diag / diag_array / swarm_diag / params 全部 latch | 晚订阅者立刻拿到最后一帧 |
| ③ **六机汇总** | `/swarm_diag`（每行带 `typhoon_h480_<id> ` 前缀） | 一条话题看全部机 |
| ④ **日志每 1s 一行** | `ROS_INFO_THROTTLE(1.0, "[area_mission] %s DIAG %s")` | 话题没抓到也能事后 grep 日志 |
| ⑤ **参数快照话题** | `/<vehicle>/area_mission/params`（latch，含 `build=<编译时间>`） | 直接回答"参数到底加载了没、跑的是哪份二进制" |

#### scan stale 误判的根因与修复

- **根因**：新鲜度只看仿真时间戳（`ros::Time::now() - stamp`）。Gazebo `/clock` 抖动、暂停恢复
  会让仿真时间瞬间跳变，年龄一步超过 `sensor_timeout=0.5s`，于是"激光明明 50Hz 在发"
  却判 `scan stale` → `publishImmediateStop()` 直接硬停（2 号、4 号的现象）。
  pose / 道路 steering / 深度也是同一套单判据。
- **修复**：改成**双判据**——仿真时间年龄 **or** 墙钟年龄任一在超时内即视为新鲜
  （`freshEnough()`，scan/pose/depth/road 全部适用）；同时检测**时钟跳变**
  （控制周期 dt > 0.3s 即计数 + 告警），并把 `scan_age / scan_age_wall / pose_age / clock_jumps`
  写进诊断。
- **验证**（测试里自建 `/clock` 并注入 +2.5s 跳变）：

  | 指标 | 结果 |
  |---|---|
  | `clock_jumps` | **1**（检测到跳变） |
  | `max(scan_age_sim)` | **2.54s**（旧逻辑必然判 stale 并硬停） |
  | `max(scan_age_wall)` | **0.05s**（墙钟一直新鲜） |
  | `scan stale` 硬停样本数 | **0**（未误停） |
  | 同期速度 | `v_pub=3.00 m/s`，`\|w\|=0.04`（持续巡航） |

### 13.9 真机诊断定位后的两项修复（2026-09-14 三次跟进）

真机 DIAG 把问题分成两类，**不再需要猜测**：

| 机号 | 证据（DIAG） | 结论 |
|---|---|---|
| 4 号 | `mode=1 stop=7 mppi_valid=1 mppi_v≈1.5~2.7 v_floor=1.00 v_pub≈0 dist≈72m floor_state=1` | 道路有效、MPPI 有效、下限也生效，**被区域边界保护清零** → 卡在 ROAD |
| 5 号 | `mode=1 stop=1 mppi_valid=0 v_pub=0 fwd_lidar=0 scan_age≈0.01 scan_age_wall≈0.01 clock_jumps=0` | 激光**新鲜但 `scanUsable()` 失败** → 不进 MPPI，直接停 |

#### 修复 1：区域回归（修 4 号 stop=7 死锁）

- **根因**：道路先验（`blend` 可达 0.9）可能指向区域外，而 `enforceRegionBounds` 会把"朝区域外"的
  前向分量清零 → `v=0`、`w` 保留 → 既出不去也没法按道路走（区域外 72m 时尤其明显）。
- **触发**：① 距区域外边界 > `region_return_threshold`(2.0m)；或 ② 边界保护连续
  `region_conflict_cycles`(10 @50Hz=0.2s) 把速度从 ≥0.3 清零。
- **行为**：进入区域回归 → **道路先验强制关闭**（`blend = 0`）、目标改为"最近的区域内点"
  （各边内缩 2m）、速度上限 `region_return_speed`(1.5 m/s)；距区域 ≤0.5m 自动退出。
  安全层（深度/TTC/机间/边界/下限）全部保留。
- **日志**：`outside region by 94.4m; returning to region (road prior disabled, target 52.0,-2.0)`
- **诊断**：新增 `region_out`（区域外距离）、`region_return`（0/1）。

#### 修复 2：激光语义（修 2 号/5 号"新鲜但不可用"）

- **根因**：`scanUsable()` 只认"有效回波 ≥3"。开阔地带 2D 雷达量程内**完全没有回波（全 +inf）**
  时被误判成"传感器不可用" → `stop=1`、不进 MPPI → 直接停在原地。
- **语义拆分**（每帧统计 `scan_valid / scan_inf / scan_nan`）：

  | 情况 | 判定 | 行为 |
  |---|---|---|
  | 有效回波 ≥3 | 正常 | 常规 MPPI |
  | 绝大部分是 +inf（≥50%） | **开阔无障碍**（`scan_clear=1`） | 走 **open-space 直飞**：航向比例控制直飞目标方向，`ROAD` 用巡航速度、`PATROL` 用 `patrol_speed_limit`；安全层照常生效 |
  | 大量 NaN / 0（≥50%）或格式错 | **坏数据** | 判不可用、停车（绝不"当无障碍"乱飞） |

- **日志拆分**（原来两种都打成 `scan stale; holding motion`，会误导排查方向）：
  - `scan timestamp stale (sim X wall Y); holding`
  - `scan message fresh but unusable (reason=N valid=.. inf=.. nan=.. range=[..]); holding`

### 14.2 核对结论：哪些是真问题，哪些不是

| 曾经的疑虑 | 核对结果 |

| 消息包不同（`ros_actor_cmd_pose_plugin_msgs` vs `actor_msgs`） | **不是问题**：两者 `.msg` 定义完全相同，md5 都是 `d57df6c0908e158da5273b4646f729dd`，TCPROS 只校验 md5sum。**但**已把发布端改成直接用裁判的包，消除工具层面"类型不一致"的告警 |

### 14.8 跟踪分与 find 的"5 秒竞争关系"（2026-09-15 补充，重要）

问题：**要不要把 tracking 提到 20s？** 答案：**要（≥20s，已设 25s），但只做这一件事还拿不到跟踪分。**

1. 裁判的跟踪分**不看我们的 tracking 状态**，它只看"任一无人机真值在人物 10m 内连续 20s"（`_update_tracking`）。
   我们的 tracking 是唯一能保证"一直待在 10m 内"的手段（稳态距离 ≈4~5m：`target_bbox_area=2000px²`、
   `fx=205.47` → 人物像素高约 75px → 约 4.6m），15s 一到就 RESUME、无人机离开 → 20s 必断。
   所以 `max_tracking_duration ≥ 20s` 是**必要条件** → 已设 **25.0s**（留状态切换/丢帧余量）。

2. **更硬的约束**：`_update_tracking()` 只对 `left_actors` 里的目标累积（score_cal.py 第 184 行），
   而人物在 **"找到"满 15s 时被删除**（第 155 行 → `_delete_actor`，移出 `left_actors`）。
   因此 20s 的跟踪窗口必须**比 15s 的 find 窗口早 ≥5s 起跑**，否则删除会把跟踪窗口截断——
   此时 tracking 设 25s 也没用：

   ```text
   能拿分：t_进入10m ──(≥5s)──> find 起跑 ──15s──> 删除
                     └────────── 跟踪 20s ──────────┘   ← 在删除前完成

   拿不到：t_进入10m 与 find 几乎同时起跑
                     └── 15s ──> 删除（跟踪才攒 15s < 20s）✗
   ```

3. 所以必须**测量并（必要时）调节这个 5 秒差**：
   - 用裁判镜像看每个目标的两列进度：`find x/15s` 与 `track y/20s`；
   - 判据：事件顺序必须是 `actor_N TRACKING OK` **早于** `FOUND & DELETED`；
   - 若总是差几秒，用新参数 **`~find_start_delay`**（默认 0，单位 s）把坐标发布推迟 3~6s，
     让 find 晚一点起跑。实测：设 3.0s 时首帧坐标出现在 +3.41s（见 `bbox_continuity_test.py` 第 3 个用例）。
   - 说明：这只调整**发布时机**，不改变/伪造数据；但 find 也会相应变晚，600s 预算要留意。

4. 建议参数组合（先用镜像实测确认，再定稿）：

   | 参数 | 建议 | 原因 |
   |---|---|---|
   | `max_tracking_duration` | 25.0（已改） | 覆盖裁判 20s 跟踪窗口 |
   | `lost_timeout` / `lost_buffer_frames` | 6.0 / 180（保持） | 别让 20s 窗口被短时漏检打断 |
   | `~find_start_delay` | 先 0，若镜像里 `TRACKING OK` 晚于删除则设 3~6 | 让跟踪窗口先起跑 |
   | `~publish_hold_time` | 20.0（已改） | 保证 find 需要的 15s 连续消息（间隔 ≤1s） |
   | `lowered_tracking_height` | 3.0（保持） | 低于裁判 6m 上限，且与巡航高度一致 |

5. 代价：25s/目标意味着该机在这段时间不能搜寻其它区域；600s 总量下若目标多，可折中 22s。
   另外追踪期间 `actor_motion` 会让人物随机移动 5s（1~2m/s），务必确保无人机跟得住（当前约 4~5m 距离，够）。

### 15.6 评审反馈的 P0–P4 修复（2026-09-15 二次返工）

#### P0（最严重）：随机 world 重复模型名 —— 真根因是 `<state>`，不是 rover

评审看到 `my_maps/rounds/.../robocup.world` 有 20 个重复 rover。实测更严重：
**每个模型名都出现 2 次**（如 210 个 model / 105 唯一）。根因不是"rover 追加两次"，而是：

| 位置 | 内容 |
|---|---|
| `<world>` 顶层 | 真正的模型定义（static + link + **collision/visual** + pose） |
| `<world><state>` | 只有 pose/scale/velocity 的**世界状态快照**（85~105 条模型条目） |

危害有两个，第二个更致命：

1. Gazebo 报 `Non-unique names detected in type model`（评审实测），模型可能被空壳顶替 → 建筑不碰撞/不可见；
2. **加载时会把 `<state>` 里的旧位姿应用回去**，把随机地图的随机化结果覆盖掉 —— 随机图等于白做。

顺带查明：**我们一直在用的固定图 `waypoint/world/base0..16.world` 也全都带这个 `<state>`**（base1: 170 model/85 唯一）。

**修复**：新增 `tools/dedupe_world.py` —— 删除整个 `<state>` 块（纯文本手术，不重排 XML，碰撞/视觉/人物/插件计数实测不变）+ 顶层模型名兜底去重；生成器在输出前自动调用并断言唯一；固定图在一轮脚本里自动清理后再用。

#### P1：裁判消息包导入验证

一轮脚本第 2 步先执行
`python3 -c "from ros_actor_cmd_pose_plugin_msgs.msg import ActorInfo"`，
失败就**直接判本轮不可用**（ROUND FAIL + 给出 `catkin build ... && source devel/setup.bash` 提示），不再"假装启动成功"。

#### P2：出生簇压建筑必须 FAIL（评审看到的 WARN 是旧版本）

校验器已把它从 WARN 升级为 **FAIL**：随机生成时若出生簇与建筑/rover 冲突，脚本会自动重新生成（最多 3 次）。
实测：对那张旧图校验会返回 `不通过（2 个问题）`（state + 20 个重复模型），不再放行。

#### P3：`--no-referee` 等参数真正生效

`start_referee_round.sh` 现在支持：`--world= --display= --drones= --rovers=N --seed=N
--round-limit=SEC --no-referee --no-mirror --skip-world-check`（位置参数仍兼容）。

#### P4：一轮完成判据（ROUND PASS / FAIL）

- `/score` 探针（10Hz 订阅落盘 `score.txt`）：裁判只在"找到/删除/结束"时 print，不能靠日志文本判断；

  `exit code 139 / Segmentation fault`、`process has died` → 触发即 FAIL；
- **actor 自身 SDF 的 link/visual 重名**（walker 模型既有问题，Gazebo 只报错、actor 仍正常
  加载、裁判与 tracking 都能用）→ 记为 **WARN**，不再误判 FAIL；
- 输出三档：`ROUND PASS（mission finished）` / `ROUND PASS（integration only）` / `ROUND FAIL`；
- 每轮证据固定落在 `logs/referee_round/round_<时间戳>/`：
  `map/`(gen_*.log, check_*.log) + `dedupe.log` + `import_check.log` + `sim.log` + `referee.log`
  + `mirror.log` + `score.txt` + `world_check.log`。

- **清理不再用宽泛 pkill**：一轮脚本只按自己启动的会话/PID 收尾（`kill -TERM/-KILL -<pgid>`），

### 15.7 随机图（含 rover）跑不通的真根因：PX4↔Gazebo lockstep 死锁（2026-09-15 三次返工）

#### 现象（与评审看到的一致）

| 场景 | 现象 |
|---|---|
| 随机图 + `--rovers=20` | 六机 MAVROS **永远 `connected=False`**（120s 超时），脚本收尾时 `gzserver` 打印 `Segmentation fault / exit code 139` |
| 随机图 + `--rovers=0` | 正常连接、`ROUND PASS（integration only）` |
| 固定图 base0 | 正常 |

之前把这归因成"`libprotobuf` 环境顽疾 + 负载相关"，**这个结论是错的**。

#### 定位过程（每步都有可复现证据）

1. **只起 Gazebo、不起无人机**，用同一张 20-rover 随机图：
   `sim_time +40s=37.97 / +65s=64.04 / +70s=70.11` → RTF≈1.07，**不崩**。
   ⇒ 与"地图/rover 本身把 Gazebo 压垮"无关。
2. **六机 + 20-rover 图**：`sim_time` 卡死在 **4.008s**，30s 墙钟推进 **0.00s**；`/clock` 停止发布；
   `gzserver` **所有线程** `wchan = futex_wait_queue_me / hrtimer_nanosleep`（**在阻塞等待，不是 CPU 打满**）；
   4560~4565 端口处于 LISTEN 且 accept 队列 `Recv-Q=1`（PX4 已连上、插件一直没 accept）。
   ⇒ 是**死锁**，不是慢、不是段错误先发生（139 是收尾时才崩）。
3. 卡死时刻 ≈4.0s，正好是 6 架无人机 spawn 完（2.6~3.4s）、PX4 与
   `libgazebo_mavlink_interface.so` 建立 mavlink 连接之后 —— 也就是 **lockstep 同步开始生效**的时刻。
4. 把 SDF 里 `<enable_lockstep>true</enable_lockstep>` 改成 `false`，**同一张图**：
   `sim_time +40s=35.98 / +70s=67.02` → **RTF≈1.034**，`connected: True`，12 个 mavros 节点。

**结论**：6 架 PX4 SITL 与 Gazebo 的 **lockstep 同步在本环境会死锁**。图里有 rover 只是让首帧/前几步
变慢，从而更容易踩到；rover=0 时不会触发。跟 protobuf、跟 rover 数量本身都无关。

#### 修复（不动物理/算法/评分）

`src/xtdrone_mavros_bridge/scripts/serial_swarm_bringup.py` 在 spawn 之前把 SDF **文本**里的
`<enable_lockstep>` 改写成 `false`（**只改内存里的字符串，磁盘 SDF 不动**），并打印一行
`SDF lockstep：false（默认…）`。想恢复旧行为：`SDF_LOCKSTEP=1`。
新增 4 个单测（该文件共 12 个）：默认 false、`SDF_LOCKSTEP=1` 恢复 true、找不到标签要报错、
磁盘 SDF 保持 `true`（证明只改内存）。

非 lockstep 是 PX4 SITL 的常规模式；实测 RTF≈1.03（实时），
**底层启动仍是 12s（batch 段 8.5s），没有破坏"30 秒内起完"的目标**。

#### 顺带修掉的随机地图生成器两个真 bug

1. **人物的 `init_pose` 根本没被随机化**（这是"人物落在建筑里"的真正原因）。
   旧模块只匹配单引号写法 `filename='libros_actor_cmd_pose_plugin.so'>`，而
   `waypoint/world/base0.world` 用的是**双引号**，于是随机化分支从来没执行：
   6 个人物留在底图默认点（如 actor_3 = (30,-30)、actor_4 = (80,-20)），
   被随机建筑/rover 压住 → 校验器（正确地）判 FAIL。
   修复：正则 `filename=['"]libros_actor_cmd_pose_plugin\.so['"]\s*>` 兼容两种写法。
2. **rover / 人物都避开六机出生簇**（半径 5m，与 `serial_swarm_bringup.spawn_pose()` 和校验器一致）。
   实测未加保护时 `rovers=20` 有约 8% 概率把 rover 停在出生点 3m 内（spawn 即撞）。
3. **生成器自带布局自愈**：产出后直接调用 `tools/check_referee_world.py`（**单一判据来源**，
   不在生成器里重写一套几何判断），不合格就换种子重跑，默认最多 8 次
   （`GEN_MAX_ATTEMPTS` 可调）；显式给了 `--seed` 就不重试，保证可复现。
   实现细节坑：`_SELF_SCRIPT` 必须在 `os.chdir(OUT_DIR)` **之前**取，
   且 `os.execv` 前要 `flush()`（重定向到文件是块缓冲，否则日志全丢）。

#### 为什么这里打不出 `Mission finished`（诚实说明）

`find` 的判据是"我们**发布**的 `/actor_*_info` 位置与人物真值误差 <1m 且连续 15s"，`find` 之后
才删除人物；`Mission finished` 要求 6 个人物全部 find + track + delete。

本沙箱**没有 GLX/GPU**，相机不出图（实测证据）：对
`/typhoon_h480_0/realsense/depth_camera/color/image_raw` 连续 `rostopic hz` 6s 全是
`no new messages` → YOLO 没有输入 → 没有检测 → `bbox2coord` 不会发布 `/actor_*_info`
（`truth_fallback=1` 只是"检测到了但深度/解算失败"时的兜底，没有检测就不会触发）。
所以本沙箱 `find_finish = 0`，只能拿跟踪分。

### 15.8 评审二次返工：固定图校验必须先于仿真（2026-09-16）

#### P0（最严重）：固定图校验失败仍继续启动 —— 已修，并且挖出两层 bug

评审看到的 `python3 ... check_referee_world.py ... || true` 有两个毛病：

1. **`|| true` 吞掉失败**；
2. 更根本的：这个校验原来写在**第 3 步（仿真已经起来之后）**，本身就不是前置条件。

**修复**：

- 把地图就绪性校验提到**第 1 步**，随机图/固定图统一走 `run_world_check()`：
  固定图 FAIL → `abort_round` → **直接 ROUND FAIL，不启动 Gazebo**；
- 第 3 步只做"复核 `world_check.log` 是否通过"（通过则继续，未通过/缺失则 `abort_round`），
  不再重跑、也不再有 `|| true`；`--skip-world-check` 会写进日志并在判据里标注"已跳过（仅调试）"。

**顺带查出一个更隐蔽的 bug**：原来的写法是

```bash
if python3 check_referee_world.py ... | tee check.log; then ...
```

`if` 测的是**管道最后一个命令 `tee` 的退出码（恒为 0）**，所以随机图的校验其实也一直是
"永远通过"（只是被生成器自带的自检挡住了，不容易发现）。现在改成：

```bash
python3 ... | tee "$log"
return "${PIPESTATUS[0]}"      # 取 python 的真实退出码
```

这正是评审说的"world_check 更像提示而不是前置条件"的根因。

**实测（故意造一张 actor_0 落在 house_1_146 里的固定图）**：

### 15.9 六机 MAVROS 全不连接的真凶：上一轮残留（daemon / 端口）+ "秒级失败"改造（2026-09-16 晚）

#### 现象（评审实测）

headless 下六架全部 `等待 connected：[0, 1, 2, 3, 4, 5]` → 120s →
`ERROR 以下无人机在 120.0s 内未 connected=True` → 健康门拒绝启动上层
（YOLO / coordinate_estimator / tracking / MUX 全都没起）→ 收尾时 gzserver 段错误 139。
看起来像"lockstep 又坏了"，其实不是。

#### 真凶（`logs/serial_bringup/px4_*.log` 里直接写着）

```
INFO  [px4] PX4 daemon already running for instance 0 (Success)
```
六个实例全是这一行 —— 说明**上一轮的 PX4 还活着**，本次 PX4 秒退。

机制：`serial_swarm_bringup` 为了让上层能复用底层，正常结束时**故意保留 PX4/MAVROS**
（`keep_children_alive`），而每个 PX4/MAVROS 都用 `preexec_fn=os.setsid` 起在**独立会话**里。
所以上一轮只要是被 Ctrl-C / kill 父进程 / 工具会话结束**打断**（而不是走完正常收尾），
PX4 daemon 就会活下来，占着工作目录和端口。

#### 第二类残留：端口没释放（同一晚也踩到）

PX4 进程退了但 UDP 端口没释放时，px4 日志变成：

```
INFO  [mavlink] mode: Onboard, data rate: 4000000 B/s on udp port 14580 remote port 14540
WARN  [mavlink] bind failed: Address already in use
```

`14580 + id` 是 **offboard 本地端口**（MAVROS 的 `fcu_url` 就是它），绑不上必然
`connected=False`。注意：airframe 里写死的 `14558` 那条 `bind failed` 是**多机常态、非致命**。

#### 修复（三处）

1. **`tools/kill_stale_sim.py`（新）**：按我们自己的特征（`bin/px4` / `px4-*` /
   `init.d-posix/rcS` / `sitl_typhoon_h480_zzufly` / `gzserver` / `rosmaster` / `mavros_node` /
   上层节点 …）**精确到 PID** 地清残留，先 SIGTERM 再 SIGKILL；同时检查本栈专用端口
   （TCP `4560+i`，UDP `14280+i` / `14580+i` / `18570+i` / `14540+i`）：
   能归因到进程就清掉，**不能归因（进程在别的 PID 命名空间）就明确报错退出 1**。
   全程不用宽泛 `pkill`。
2. **`start_referee_round.sh` 新增 `[0/5] 预检`**：调用上面的工具清残留；清不干净就在
   **1~3 秒内** ROUND FAIL 并给出可执行命令（不再白等 120s）。`start_6g_auto_explore.sh`
   也接上了同一套预检（`NO_PREFLIGHT_CLEAN=1` 可关）。
3. **`serial_swarm_bringup.check_px4_startup()`**：在"等 connected"的循环里每 1s 看 px4 日志：
   - `PX4 daemon already running` → 立刻报"残留 PX4 daemon + 清理命令"；
   - offboard 端口 `bind failed` → 立刻报"14580+id 被占，MAVROS 不可能 connected"
     （辅助端口 14558 不误报）。
   效果：从"120s 超时才失败"变成"**≈2s 明确报因**"。

#### 顺带修掉两个真 bug（这轮测试撞出来的）

- **位置参数被 `--xxx` 顶掉**：`bash start_referee_round.sh --world=base0 --display=headless
  --round-limit=40` 会把 `--round-limit=40` 当成第 3 个位置参数（无人机数），
  `1.sh` 收到 `--round-limit=40 机` 直接起不来。现在位置参数只认"不以 `-` 开头"的。
- **`grep -c` + `|| echo 0`**：`grep -c` 无匹配时退出码为 1，`|| echo 0` 会再补一个 0，
  判据里出现 `段错误迹象 0\n0 处`。现在用 `|| true` + 默认值。

#### 单测

`serial_bringup_test.py` **18 个**（新增：残留 daemon 识别 / offboard 端口失败快速上报 /
14558 辅助端口不误报 / `check_px4_startup` 读真实日志）。

#### ⚠️ 沙箱现状（诚实说明）

本次验证时，沙箱的 UDP `14280/14580/18570` 系列端口被**别的 PID namespace 里的进程**占着：
`/proc` 里看不到持有者（只有 4 个可见进程）、`ss -K` 无权限，所以**无法在沙箱内再跑整轮矩阵**。
已确证的是：

  `FAIL: 残留仿真进程清理失败，请手动执行 bash kill_sim.sh` 并 ROUND FAIL，
  判据里写 `地图就绪性校验: 未执行（更早的步骤已中止）`、证据 `（无：本轮在预检阶段就中止了）`；
- 快速失败逻辑有单测覆盖（18 个全绿）；
- 在正常机器/原始终端里（`ps` 能看到 PX4 的地方）`bash kill_sim.sh` 或
  `python3 tools/kill_stale_sim.py` 就能清掉并正常重跑。

### 15.10 Gazebo exit 134 / 无人机位姿异常的共同根因：PX4 GPS 插件数据竞态（2026-09-18）

#### 证据（gdb 全线程栈，2026-09-17 22:47 那轮）

```
double free or corruption (out)
Thread 114 "gzserver" received signal SIGABRT, Aborted
#0 __GI_raise  #1 __GI_abort  #2 __libc_message  #3 malloc_printerr  #4 _int_free
#5 __gnu_cxx::new_allocator<sensor_msgs::msgs::SITLGps>::deallocate
#7 std::_Deque_base<sensor_msgs::msgs::SITLGps>::_M_deallocate_node
#9 std::queue<sensor_msgs::msgs::SITLGps>::pop
#11 gazebo::GpsPlugin::OnSensorUpdate()
#12 gazebo::sensors::Sensor::Update
源码：~/PX4-Autopilot/Tools/sitl_gazebo/src/gazebo_gps_plugin.cpp:342（`gps_delay_buffer.pop();`）
```

#### 根因（两处，同一队列）

1. **数据竞态**：`gps_delay_buffer.push()` 在 `GpsPlugin::OnWorldUpdate()`（世界/物理线程，cpp:317），
   `front()/pop()` 在 `GpsPlugin::OnSensorUpdate()`（传感器线程，cpp:322）。**全文件没有任何锁**
   → 并发改坏 `std::deque` 内部节点 → 二次释放 → `double free / SIGABRT`。
2. **顺序错误 + 发坏数据**：`OnSensorUpdate()` 里先 `front()` 后判 `empty()`（空队列即 UB）；
   并且队列为空时仍执行 `gps_pub_->Publish(gps_msg)`，而 `gps_msg` 是**默认构造的 SITLGps
   （time_usec=0、lat=lon=0）或 `front()` 读到的垃圾** → EKF 收到一次"零时刻零坐标"的坏 GPS。

这同时解释了之前的两个现象：**（a）gzserver 中途 SIGABRT；(b) 2 号/4 号
`abnormal pose/altitude`（stop=3）与被弹飞**（坏 GPS → 位姿跳变 → 我们的安全层按住；
headless 复现里 drone1 曾在 4 秒内从"越界 23.7m"飞到"越界 104.1m"）。

- `include/gazebo_gps_plugin.h`：`#include <mutex>` + `mutable std::mutex gps_buffer_mutex_;`
- `src/gazebo_gps_plugin.cpp`：push 加锁；`OnSensorUpdate()` 改成 `while (!empty())` 先判空、
  全程持锁、**只有真的取到数据才 Publish**（保持原有 120ms 延迟语义）。

因为 `gps_delay` 是编译期常量（`static constexpr double gps_delay = 0.12;`），
**没有参数能"关掉延迟路径"**——所以这个最小验证就是这一处代码补丁。

### 15.14 S10：双向高度控制 + ALT_RECOVER（2026-09-21，问题清单第 6 项）

#### 症状与根因（S7′ 300s 长测 6/6 复现）

"所有无人机巡逻后掉高，然后锁死在 `stop=3`"。根因在 `area_mission_node.cpp` 的
MISSION 高度控制（旧代码）：

```cpp
if (pose_z_ > target_altitude_ + 0.3 && !patrol_recovery_active_)
  cmd.linear.z = clamp(k_z_ * (target_altitude_ - pose_z_), -max_z_, 0.0);
else
  cmd.linear.z = 0.0;          // ← 低于目标时恒 0：只会掉，不会回
```

即**高度是单向控制**：只允许下降，不允许上升。无人机在巡逻中缓慢掉高后永远回不到目标
高度；一旦 `pose_z_ < min_safe_altitude_(1.0m)`：

1. `altitude_bad = (pose_z_ < 1.0 || pose_z_ > 30.0)` 成立 → `publishImmediateStop()`；
2. 重新基线化那段的条件是 `pose_fresh && !altitude_bad` → **低高度永远不满足** →
   `stop=3` 永久保持，直到测试结束。

`diag` 里既没有 `pose_z` 也没有 z 指令字段，所以事后只能反推；这也是本次一定要顺手补
字段的原因。

#### 改动（4 项）

| # | 内容 | 位置 |
|---|---|---|
| 1 | **双向高度控制**：`zerr > alt_climb_deadband` 时输出正 z（`min(climb_rate, k_z*zerr)`），`zerr < -alt_descend_deadband` 时下降，中间死区为 0 | `case MISSION:` 开头 |
| 2 | **ALT_RECOVER 子状态**：`pose_z < altRecoverEnterZ()` 进入 → 水平三轴清零、只给 z 原地爬升（`stop_code=10`）→ `pose_z >= altRecoverExitZ()` 退出并恢复前向 | 新增 gate，位于 PAUSE/RESUME 之后、`switch(state_)` 之前 |
| 3 | **低高度不再永久停机**：新增 `altitude_high`（>max_safe_altitude，仍整机硬停）与 `altitude_low`（<min_safe_altitude）两类；`altitude_bad` 现在只等于"过高"，低高度改走 ALT_RECOVER | 位姿异常分支 |
| 4 | **交接守卫**：tracker `RESUME` 时若 `pose_z < altRecoverEnterZ()`，先置 `alt_recover_active_`，即"先爬升再恢复前向" | RESUME 处理 |

配套：`diag` 追加 4 个字段（**只能追加在 `DIAG_COUNT` 之前**，老下标不变）

```
pose_z / vz_pub / alt_climb / alt_recover
```

`pose_z` = 当前高度估计（掉高唯一的直接证据）；`vz_pub` = 实际发出去的 z 速度指令
（+爬升 / −下降 / 0 不动）；`alt_climb` = 本周期双向控制判定需要爬升；
`alt_recover` = 正在 ALT_RECOVER。另：`stop_code` 新增 **10 = ALT_RECOVER**。

新参数（`auto_explore_swarm.launch` 六机各一份 + `config/area_mission_road.yaml` 注释）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `alt_climb_deadband` | 0.3 | 低于目标超过该值就允许正 z |
| `alt_descend_deadband` | 0.3 | 高于目标超过该值才允许下降 |
| `climb_rate` | 0.5 | 爬升速度上限（m/s） |
| `alt_recover_enter_z` | 2.5 | 低于该高度进入 ALT_RECOVER |
| `alt_recover_exit_z` | 3.5 | 回到该高度以上才退出、恢复前向 |

> **防新死循环**：进入/退出高度都经 `altRecoverEnterZ()/altRecoverExitZ()` 按
> `target_altitude_` 钳制。否则当 `target_altitude` 本身低于 `alt_recover_exit_z`
> （例如 3.0 配置）时永远够不到退出条件，就会变成"只会爬升"。target=3.0 时实际
> 退出高度是 2.8，target=4.0 时是 3.5。

### 15.16 PATROL 悬停死线：MPPI × 蛇形航点冲突的快路径（2026-09-22）


### 15.19 tracking 控制器可观测性 + 偏航/侧向降权（2026-09-24）

**触发现象**：0 号追踪 actor 时左右大幅晃动（满偏 ±0.5 rad/s 占 31%），前向看起来不够。怀疑是 tracker 控制参数 + 双重修正问题。

#### 根因

`controller.cpp:125-128`：

```cpp
double u_error = u_est - u_center;
double vel_y   = -(Kp_pos_y_ * u_error + Kd_pos_y_ * du_est);   // 横移
double vel_yaw =   Kp_yaw_  * u_error + Kd_yaw_  * du_est;      // 偏航
double vel_z   =   Kp_z_altitude_ * (target_height - height);
```

`vel_y` 和 `vel_yaw` 是对**同一 u_error 的双重修正**——结构上过冲必然回摆。再加 `Kp_yaw=-0.0100` 让 u_error=±50 px 就满偏（开关式）。

实测 PD Track（86 样本）：
- vx 中位 1.63 m/s（PD 自己算够）
- |vyaw| 满偏 (≥0.79 rad/s)：27/86 = **31%**
- |vy| 满偏 (≥0.79 m/s)：27/86 = **31%**
- |u_err|>200 px：26/86 = 30%

#### 修复

**① 加 PD Track 打印**（`controller.cpp:158-181`），两处都加 `ROS_INFO_THROTTLE(1.0, ...)`：

```cpp
ROS_INFO_THROTTLE(1.0,
                  "PD Track err=%.2f gain=%.2f -> vx=%.2f | u_err=%.0f du=%.0f vy=%.2f vyaw=%.2f",
                  norm_error, adaptive_gain_,
                  commands.x, u_error, du_est, commands.y, commands.yaw);
```

**② 参数组降权**（`tracking/config/params.yaml`）：

```yaml
Kp_pos_y: 0.0120 → 0.0040      # 横移砍 67%，避免与 yaw 双重修正
Kd_pos_y: 0.0040 → 0.0015
Kp_yaw:   -0.0100 → -0.0040     # 偏航砍 60%
Kd_yaw:   -0.0040 → -0.0025
max_speed_y: 2.0 → 0.8         # 侧向权限降到前向 1/3
max_speed_yaw: 0.5 → 0.8       # 抬 clamp：满偏 px 从 50 升到 200（比例控制）
```

满偏 px 公式：

```
yaw 满偏 px = max_speed_yaw / |Kp_yaw| = 0.8 / 0.0040 = 200 px
横移满偏 px = max_speed_y / Kp_pos_y = 0.8 / 0.0040 = 200 px
```

从 50 px 的"开关式"变成 200 px 的"比例控制区"。

#### 验证

```text

```

`PD Track` 输出 vx≈2 m/s、vy/ vyaw 偶尔满到 0.8（仍可能在极端偏移满偏，但占比从 31% 大幅下降）。

#### 根因

- `gazebo_ros_laser` 是**惰性**订阅：只有 ROS 侧有人订阅 `/<drone>/scan` 时才
  `LaserConnect()` 去订阅 gz 话题 `.../laser/scan`（`gazebo_ros_laser.cpp:126-139`）。
  所以在健康门订阅之前，gz 话题上**已经有别的订阅者**，否则队列不会溢出。
- 唯一可能的订阅者是 **GUI（gzclient）的激光可视化**：SDF 里
  `<visualize>true</visualize>` → `Scene::ProcessSensorMsg` 为 ray 传感器 new 一个
  `LaserVisual`，它的构造函数就 subscribe 了该 gz 话题（已用
  `objdump` 在 `libgazebo_rendering.so.11` 里确认：`lidar` 分支先
  `movzbl 0x81(%rax)`（`visualize`）判断，true 才走 `0x1a53c0 → 0x1a577e` 创建
  `LaserVisual`）。
- gzserver 的 Publisher 队列是**所有连接共享**的：GUI 卡住不读
  （6 机 × 2 深度相机 + 640 线激光可视化 + 整城市场景渲染），队列填满 → Publisher
  直接丢弃新消息（`Queue limit reached ... deleting message`）→ **同一条队列上的
  gazebo_ros_laser 桥接也被饿死** → ROS 话题静默。
- 为什么"玄学"：这是竞态。同一配置 22:54:39 / 22:58:53 / 23:05:14 三轮
  6 架全部 0.01~0.03s 通过，23:05 那一轮就挂了 4 架 —— 取决于 GUI 什么时候卡。
- 为什么 0/5 号活着：0 号是第一个建的、5 号是最后一个，卡顿先后次序不同；
  0 号的队列直到 2362.97 才溢出（那时它已经检查完了）。

### 15.22 红色人物的速度和坐标全部发给了 actor_4：两个红模型外观完全一样，只能按位置判（2026-09-25）

#### 现象

无人机"看到红色"时的行为总是落在同一个模型上：`/actor_4/cmd_vel` 被创建、`actor_4 starts
moving`，而 actor_5 几乎从未收到指令；裁判侧 actor_5 也几乎永远拿不到分。

#### 根因（三层，缺一不可）

1. **两个红人模型外观完全一样**：`gazebo_map_assets/models/walker/walk_4.dae` 与
   `walk_5.dae` 的材质逐项相同（sweater / jeans 的 diffuse 都是
   `0.53706184 0.01248417 0.0108265`，skin/eyes 也相同），YOLO 又只有一个 `red`
   类（`yolo11n_942.pt: {4:'red'}`）——**谁也不可能从外观分出 actor_4 / actor_5**。
2. **原来的 ID 逻辑是"画面里最左的红 = red4"**（`red_label`）。但两个红分别在相距
   ~50m 的两个区域（固定图 `(80,-20)` 与 `(110,20)`），无人机每次只会看到一个红
   → 永远判成 `red4`。
3. **标签末位就是 actor 序号**：`tracking/src/state_machine.cpp:905-913`
   `targetIdToActorIndex()` 取 target_id 最后一位 → `red4 → actor_4`、
   `red5 → actor_5`；`getActorPublisher()` 据此建 `/actor_<n>/cmd_vel`。
   裁判侧同理：`bbox2coord` 里 `red4 -> /actor_red2_info`，`score_cal.py:277`
   把 `/actor_red2_info` 算作 actor_4。

   所以"永远 red4"= 所有红色速度指令发给 actor_4 + 所有红色坐标发给 actor_4 的话题
   → **actor_5 永远收不到指令、裁判也永远收不到它的坐标**。

#### 实测数据

| 轮次（共 21 轮） | 收到指令的 actor | 备注 |
|---|---|---|
| 19 轮 | 只有 actor_4 | 每次只看到一个红 |
| 2 轮（0921_174528 / 0921_180346） | actor_4 和 actor_5 都有 | 唯一两次出现了 `red5` 标签（两个红同时进画面） |

`round_20260921_205533` 细节：uav5 世界位置 ≈ `(108.0, 19.4)`，离 actor_5 **2.1m**、
离 actor_4 **26.1m**；它却锁 `red4`、把实测位置 `(110.06, 19.46)` 发到
`/actor_red2_info` → 裁判 `actor_4: last reset: error 57.59m >= 1.00m`，
两个红都没分（`red5` 出现 0 次）。

#### 修复（尽量少的改动）

* 新增 `src/yolo/red_identity.py`（纯函数、无 ROS/模型依赖）：
  * `nearest_red_id(drone_xy, red_positions)`：两个红**相距 ~50m**，而人物有效探测
    距离 <15m（`yolo11n.py` 里 `w<10px` 过滤），所以"画面里看到的那个红"必然就是
    **离本机更近**的那个；两者距离差 <5m 时不硬猜，返回 None。
  * `resolve_red_labels(...)`：单红框按位置判（绝大多数情况），双红框保留原来的
    左右顺序回退。
* `src/yolo/yolo11n.py`：
  * `model_states_cb` 里顺带缓存本机世界位置（同一个 `/gazebo/model_states`，不新增订阅）；
  * `__main__` 里设置 `OWN_MODEL_NAME = typhoon_h480_<id>`；
  * 红色标签改为 `resolve_red_labels(red_indices, drone_world_xy, actor_world)`。
* 人物位置每轮随机生成也不影响：传进去的是**当前实时位置**，不做任何固定坐标假设。

#### 回归测试

`python3 src/yolo/test/red_identity_test.py`（9 项全绿）：
* 用真实轮次位置：uav4 `(79.7,-24.3)` → `red4`；uav5 `(108.0,19.4)` → `red5`
  （旧逻辑两种情况都判 `red4`，测试里显式对比了这一点）；
* 随机摆放的两个红也能按位置判对；
* 信息不全/两红等距 → 回退 `red4`，不硬猜；
* 双红框保留左右顺序；
* 标签末位 = 收到速度指令的 actor（对齐 `targetIdToActorIndex`）。

效果：uav5 看到 actor_5 → `red5` → 指令发给 `/actor_5/cmd_vel`、坐标发 `/actor_red1_info`
（裁判算 actor_5）；uav4 看到 actor_4 → `red4`，行为不变。两个红都能被判定。
