### ★ 2.1.1 坐标系换算是这块的核心（团队标注"重要踩坑"，实测确认）

> **mavros `local_position/pose` 的 ENU 原点 = 无人机出生点 (-17,-3)，不是 Gazebo 世界原点**
> ⇒ **ENU = 世界坐标 + (17, 3)**
> ⇒ `.world` 文件里的道路坐标是**世界坐标**，**不能直接搬进 launch** ✗
> ⇒ 旧 `task_manager` 的 `mission_*.json` 是**世界坐标**，只在旧系统（`pose_init` 补偿）里才有效 ✗

三重证据：① 出生点处 mavros 位姿 ≈ (0.13,-0.03)，home=(0,0)，而世界系是 (-16.9,-3.0)；
② `pose_init` 源码 `drone_offsets = {"typhoon_h480_0",{-17,-3,0}}`（local + offset = 世界系）；
③ PX4 sitl_gazebo 的 GPS 原点 = 世界 (0,0)，但 EKF 局部原点锚在首帧/出生点。

> **对我们的意义（重要）**：我在演练里写的 `offboard_aim.py` 用「本机世界坐标 − 本机 local 坐标 = 偏移」
> 现算偏移 ✓ 是等价的 ✓；但**直接把世界坐标当 ENU 用**就是团队踩过的坑 ✗ ——
> 我此前"目标 (161, 2.9) 飞 160 m"的结果 = `150(世界) + 17(偏移) − 6` ✓ 数学对 ✓，
> 真正的问题是**位置类 setpoint 没被位置控制器执行**（见 §5，非坐标系问题）✓

### 2.2 寻路逻辑（`src/auto_explore/`）——**当前方案是"视觉道路跟随 + MPPI"，不是激光 A\***

> ⚠️ **重要更正**：本方案初稿曾把 `best.pt`/视觉道路跟随划到"不取" ✗ —— 那是错的。
> 交接文档 §7.1 明确：**"ROAD 阶段已不再使用固定的中间道路航点"** ✓，
> 当前实际链路是 **`auto_explore_swarm.launch` + `area_mission_node`**，
> 并明确写明"**不使用旧的 `task_manager` JSON 航点链**"、`start_old_six_navigation.sh` **禁止使用** ✗。
> **激光/深度是最终防撞层**，不是主寻路 ✓。

#### (a) 视觉道路跟随（`scripts/road_follow.py`，16.7 KB）

- 每架无人机跑一个 `road_follow.py`，订阅**自己的 RGB 相机** `/typhoon_h480_<id>/realsense/depth_camera/color/image_raw` ✓
- 用 **`best.pt`**（Ultralytics **YOLO11n-seg**，`nc=1, names={0:'road'}`，见 §2.4）做**语义分割**，
  在下方 ROI 内估计道路候选区域的**中心偏差 / 道路方向 / 置信度 / 宽度** ✓
- 发布 `/typhoon_h480_<id>/road_follow/steering`（`geometry_msgs/Vector3`：`x=横向偏差, y=方向偏差, z=置信度`）✓
- **不再依赖道路颜色/亮度/OpenCV 阈值**（曾用，现改为分割 mask 的连通方向与宽度 ✓）
- ROI **按机体 roll/pitch 动态调整**并做滚转补偿（读 `mavros/local_position/pose`）✓
- 候选组 `[heading_norm, lateral_norm, confidence, width]` 按"与目标方向夹角 + 置信度 + 宽度 + 横向偏差"评分；
  切换需满足 `road_candidate_switch_margin` 且连续 `road_candidate_confirm_cycles` 个控制周期 ⇒ **避免路口左右振荡** ✓
- 道路短时丢失：保持上一帧结果 **0.6 s** 并衰减置信度（不再单帧失败就清零速度 ✓）；
  hold 超时后走"有界、低速的目标方向 MPPI 接近"，**不再无限原地旋转** ✓
- 模型与推理参数由 `auto_explore_swarm.launch` 下发：
  `road_model`（**默认 `$(find auto_explore)/../../best.pt`** ✓）、`road_class`、`infer_imgsz`、`infer_conf`、
  `infer_iou`、`infer_device`、`infer_max_det` ✓；启动器 `scripts/road_follow_gpu.sh` ✓
- 调试图：`/typhoon_h480_<id>/road_follow/debug_image` ✓

#### (b) 区域任务（`src/area_mission_node.cpp`）

- 状态机 **`TAKEOFF → ROAD → PATROL`** ✓
- **ROAD**：以视觉结果作道路方向先验，由 **ROAD-MPPI** 综合"目标方向 + 激光距离场"生成指令；
  到最终区域目标的 GPS/EKF 距离用于**到达判定**（六机 `wp_reach_tolerance` 统一 **10 m** ✓）
- 距最终目标 ≤ `road_approach_distance`(默认 20 m) 后：目标方向显式为主（**80% 目标 / ≤20% 道路先验** ✓）
  ⇒ 可以离开"不通向航点的道路" ✓
- **进度监测**（`progress_window` 窗口内至少减少 `minimum_progress`；连续 `progress_bad_windows`
  个坏窗口或距离增加超 `wrong_branch_distance` → 进入有界 `road_recovery_duration` hold/search，
  停前进、原地搜索、重置距离基线）⇒ **不盲飞穿楼** ✓（默认 8.0 s / 1.5 m / 5.0 m / 2 窗口 / 5.0 s）
- **PATROL**：区域内缩 5 m、间距 8 m 的**往复式蛇形航线**持续覆盖，控制层阻止越过区域边界 ✓
- ROAD 阶段有**速度渐增限制**（0.8 m/s²）与**俯仰限速**（>~0.08 rad 逐步降速）⇒ 抑制"点头振荡" ✓
- 分段速度：距目标 >20 m 用 `road_min_speed`(默认 3.0 m/s) 高速巡航；≤20 m 用 `road_approach_speed`(1.5)；
  PATROL 1.5 ✓；**ROAD 与 PATROL 用各自独立的 MPPI**，避免速度目标互相覆盖 ✓
- 达到判定补充：距目标 ≤2 m 可到达；另有"≤8 m + 新鲜深度 ≤2 m + 连续 5 周期"（对应目标落在房区内）✓
- **六个区域与无人机分配固定**（世界/GPS 平面）：

| 区域 | 矩形范围 | 无人机 | 目标航点 |
|---|---|---:|---|
| 1 | `[-50,0]×[-50,0]` | 0 | `(-35,-35)` |
| 2 | `[-50,0]×[0,50]` | 1 | `(-35,35)` |
| 3 | `[0,50]×[-50,0]` | 2 | `(20,-20)` |
| 4 | `[0,50]×[0,50]` | 3 | `(20,20)` |
| 5 | `[50,100]×[-50,0]` | 4 | `(70,-20)` |
| 6 | `[50,100]×[0,50]` | 5 | `(70,20)` |

#### (c) MPPI 局部规划（`config/mppi_params.yaml` + §7.5 安全层）

| 参数 | 值 | 说明 |
|---|---|---|
| `mppi_num_samples` / `update_rate` / `horizon` / `dt` | 1500 / 20 Hz / 16 / 0.10 | 总前视 ≈1.6 s（六机 CPU 吃紧时可降到 100×16 ✓）|
| `mppi_v_des` / `max_v` / `max_w` | 3.2 / 4.5 / 1.2 | 巡逻巡航 |
| `road_mppi_v_des` / `road_mppi_max_v` | 3.5 / 5.0 | ROAD 独立规划器 |
| `mppi_obstacle_weight` / `field_radius` / `field_res` | 100.0 / 20.0 / 0.15 | 激光距离场代价 |
| `depth_obstacle_weight` / `depth_grid_radius` / `depth_grid_res` | 40000.0 / 8.0 / 0.25 | 深度栅格代价 |
| `mppi_safe_radius` | 2.0（运行时 `max(2.0, |v|*0.8)`）| 速度相关安全半径 |

**安全层（MPPI 之后执行，§7.5）**：深度急停、TTC 急停、**位姿单次跳变 >4 m 停止**、**飞行中高度 <1 m 停止**、
机间避让、边界保护；**`LaserScan` 无效/全无效/量程非法/有效回波不足 ⇒ MPPI 标 invalid、任务节点立即停车**
（不把空扫描当无障碍 ✗）；`range_max`/无回波值**不写入**距离场 ✓；急停类动作**绕过平滑器**直接清零速度 ✓

### 2.3 追踪逻辑（`src/tracking/` + `bbox2coord_node.py`）

**团队已修的问题（`DIAGNOSIS_TRACKING_DELETE_2026-09-28.md`）**：

| 现象 | 根因 | 修法（我们可借鉴的） |
|---|---|---|
| 追了两分钟人物也不被删 | 追踪期间一直发**深度解算**坐标，误差常 >1 m ⇒ 裁判"连续 15 s、误差<1 m"窗口被反复清零 | **发布前量误差**；`publish_hold_time` **实测默认 3.0s**、`min_publish_span` **实测默认 0.0**、`publish_min_interval` **实测默认 0.6s**（文档里写的 0.1s 是 9-28 那版 ✓ 以代码为准）、`max_blind_publish 1.5s`、`range_gate`（ROI 平均深度 vs 人框高度反推距离差 >max(3m,80%) 视为失败）|
| 没被追踪却被删除 | 旧 `publish_hold_time=20s` + `min_publish_span=18s` 把"只追几秒"**补发成 15 s** 连续消息 | **补发只用于填毛刺**（裁判只要求间隔 ≤1 s），不替裁判伪造 15 s ✓ |
| 追一个已消除的人 | 不知道人物已被判消除 | **订阅 `/left_actors`**（裁判把它移出名单=已消除）立即停发/归还控制权 ✓ |
| 被一个人拖住 325 s | 无追踪时长上限 | `state_machine/max_tracking_seconds=90s` + `reacquire_cooldown_seconds=60s` ✓ |

**裁判判据（`score_cal.py:170-220`，团队实测确认）**：
`/actor_*_info` 上 **连续 15 s** + 每条与真值**误差 <1 m** + 相邻消息**间隔 ≤1 s** → 才 `delete_model` ✓
（**跟得近 ≠ 会被删**，只有"报得准且连续"才算 ✓）

**⚠️ 合规沿革（已核验：10.12 里这点已清理干净 ✓）**：
`DIAGNOSIS_TRACKING_DELETE_2026-09-28.md`（9-28 那一轮的记录 ✗）描述过"与真值比对、超差走真值兜底"，
那是**调试期的做法** ✗，作者也标注了 `TRUTH_FALLBACK=0` = "正式比赛口径（超差帧不发）" ✓。
**实测 10.12 的 `src/yolo/bbox2coord_node.py`（573 行）里已完全没有任何 `truth` 字样** ✓✓
（`grep -rn truth` 零命中 ✓）⇒ **10.12 就是我们该迁的合规版本** ✓；
我们迁移后同样**一律走合规路径**：`range_gate` + 超差帧**不发**（宁漏一帧，不清零裁判 15 s 计时）✓
