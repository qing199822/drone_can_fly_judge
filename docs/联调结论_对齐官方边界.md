# 双机联调结论与"对齐官方"边界（一页纸）

> 结论时间：2026-10-11 ｜ 场景：组委会裁判端（本机 192.168.12.101）↔ 参赛队算法机（192.168.12.102）
> 一句话：**裁判端无问题且已与官方对齐；"消除不了"的根因在算法侧到裁判端的图像/深度传输拥塞，修法全部在参赛队一侧，裁判端不需改动。**

---

## 一、三条结论

1. **裁判端计分链路本身是好的**（已独立自测，见第四节）：
   真值坐标连续上报 25 s → **发现 +50 且消除 +100（目标被移出 `/left_actors`）**；偏 5 m → 0 分；NaN → 官方缺陷下被误判为发现（已反馈组委会）。
2. **接口与合法性都正常**：六个 `/actor_*_info` 均建立 TCPROS 连接；六架 `armed=true / OFFBOARD`；云台指令正常。
3. **根因是链路拥塞导致深度与检测框不同步**：36 s 内六路合计仅 1 条有效坐标；164 个检测框里 160 个框中心的 5×5 深度区域无有效深度 → 解算节点直接跳过发布（`bbox2coord_node.py:166`）。
   本地能消除，是因为本机 Gazebo 与算法同机、图像不经网络、时间同步与帧率正常。

## 二、边界：哪些必须逐字官方，哪些属参赛队自由

| 项 | 必须**逐字官方**（裁判端，不改） | 属**参赛队自由**（算法侧自行优化） |
|---|---|---|
| 世界 | `robocup.world`（组委会生成） | — |
| 机型 | 组委会的 `typhoon_h480_2d_lidar_nudt`，或赛前申报的自有模型 | 申报模型的内容（传感器/装配） |
| 出生点/端口 | `(-17,-3)(-14,-3)(-17,0)(-14,0)(-17,3)(-14,3)`、`z=1`、`tcp 4560+i`、`udp 14560+i`、`fcu_url udp://:2454i@localhost:3458i` | — |
| 人物 | 官方 `control_actor.py`（含逃逸：被报告后 20 m 内触发、2 m/s 逃向"离最近无人机最远的角"） | — |
| 计分 | 官方 `score_cal.py`（`err=1 m`、`间隔≤1 s`、`连续 15 s` → 判消除 +100） | — |
| **图像/深度怎么传** | **不由裁判端决定**（官方插件按需/懒发布，谁订阅谁承担流量） | ✅ 订阅哪些话题、几个节点订阅、是否压缩、处理频率 |
| **相机内参怎么用** | 裁判端只发布 `CameraInfo` | ✅ 读 `K` 还是写死、外参标定 |

> 因此：**"换压缩""去重复订阅""改内参"都属于算法侧整改**，不构成对裁判端的修改要求。

## 三、算法侧整改项（3 条，均不需改裁判端）

### ① 改订压缩流（收益最大，官方插件已自带）
裁判端**已经在发布**（懒发布，订阅才有流量）：
```
…/realsense/depth_camera/color/image_raw/compressed        ← JPEG
…/realsense/depth_camera/color/image_raw/compressedDepth   ← PNG 16bit 深度
…/realsense/depth_camera/color/image_raw/theora
（stereo_right 同样三套）
```
把订阅从 `image_raw` 换到 `…/compressed` + `…/compressedDepth` → **流量约降一个数量级**，候选帧率不变，**裁判端零改动**。

### ② 消除重复订阅（成倍放大项）
ROS 对**每个订阅者**单独建连接、各发一份。单机原始量级：`depth ≈ 21.3 MB/s`、`color ≈ 16.0 MB/s` → 6 机约 **224 MB/s**（每话题 1 个订阅者）；**N 个订阅者就是 N 倍**。
做法：**1 个 relay 订阅 → 本地 fan-out**，或把 YOLO / 解算 / 追踪合并进一个进程。

### ③ 内参改为运行时读 `CameraInfo.K`（现在算错几何）
裁判端实测发布：
```
K = [554.254691191187, 0, 320.5, 0, 554.254691191187, 240.5, 0, 0, 1]
```
| | fx | 对应 FOV（640 宽） |
|---|---|---|
| 裁判端实际 | **554.25** | **1.047198 rad**（= 官方 `realsense_camera` 值、当前 SDF 的 `horizontal_fov`） |
| MPPI 写死 | 205.47 | **2.000 rad**（= 改动前的旧值） |
⇒ MPPI 内参需更新为 554.2547，**更稳妥是运行时读 `K`**（避免 SDF 一改就错）。
